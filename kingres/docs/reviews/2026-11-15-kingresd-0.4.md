# Second independent review of kingresd (control-plane), contract 0.4.0

Commit reviewed: `a51d630d53` (branch `kingres-18`). Reviewer: independent, not the author of the code, the first
review or the fix round. All file references are repository-relative at that commit, `kingres/control-plane/` is
abbreviated `cp/`, and line numbers are those of the commit.

## Scope and method

`kingres/docs`) into a scratch directory and only the export was read. The first review
(`kingres/docs/reviews/2026-11-14-kingresd-control-plane.md`) and the worklog entry about the fix round were read first.
Read closely, in full or nearly so: `internal/httpapi` (guard, middleware, cookies, headers, forward, handlers for core,
members, instance, monitor), `internal/auth` (session, ratelimit, revalidate), `internal/internalapi`, `internal/pki`

### CP2-01 (high) — a certificate is enough to impersonate any role by name

**Where.** `cp/internal/httpapi/forward.go:160-225` (`ServeForwarded`), `cp/internal/httpapi/guard.go:226-251`
(forwarded branch of `checkSession`), `cp/internal/internalapi/internalapi.go:72` and `:299-304` (`POST /forward` is
`ToLeader`: any peer with a valid certificate), `cp/internal/pki/pki.go:446` (`VerifyPeer` checks chain, usage and
revocation only).

**What happens.** The first review's CP-07 asked that the leader should not believe a forwarding peer's claimed
identity. The fix (`guard.go:233-238`) requires the claimed cluster roles to be a *subset* of the role's current roles
and then authorizes with the *current* roles (`sess.ClusterRoles = cur`). The claim therefore adds nothing: a peer only
has to name an existing role and claim no roles or the right ones. The peer needs no password, session, CSRF token or
setup token, and the leader writes the audit event with the forged actor. `ServeForwarded` also calls
`Proxy.Allow(ctx, fr.Identity.Username)` (`forward.go:218`) *before* any check, although `Proxy.Allow` is documented
"call it after a successful sign-in only" (it writes `pg_ident.conf` and reloads PostgreSQL for every distinct name a
peer sends).

**Scenario.** A server that holds a cluster certificate (a compromised member, or a server in the middle of being added,
see CP2-02) sends over the internal API
`POST /internal/v1/forward {"operationId":"setRoleClusterRoles","pathParams":{"roleName":"mallory"},"identity":{"username":"root_admin","clusterRoles":[]},"body":...}`.
The leader runs the operation as `root_admin`.

**Confirmed.** Test on the leader harness (`twoServers`, role `tester` = admin): `ServeForwarded(ctx, "any-peer", {createGrant, identity {tester, claimed []}})`
and with claimed `[kingres_admin]` both pass the guard and reach the handler (status 422 `unsupported_operation`
only because the test harness has no Ops); claimed `[kingres_readonly]` gives 401. Nothing but the name is checked.

**Fix.** Bind the identity to something the leader can verify: a short-lived assertion signed by the forwarding server
that names the session id, issued only at login on that server and checked against a per-server nonce, or at least
require the forwarding peer to be an active member (not pending) and record the peer in the audit actor. Move
`Proxy.Allow` after the guard. State the trust model ("one compromised member is a compromised cluster") in
`internal-api.md` if it is accepted.

### CP2-02 (high) — `kingres_ops` can obtain `kingres_admin`

**Where.** `kingres/api/openapi.yaml` operation `addServer` (`x-required-role: kingres_ops`, line 858);
`cp/internal/membership/add.go:196-262` (`AddServer`), `:90-180` (`introduce`), `:561-575` (`stepAddGlobals`),
`cp/internal/cluster/globals.go:24-30` (the globals include `rolpassword`, the SCRAM verifiers).

**What happens.** Joining through the wizard needs administrator credentials (`membership/handle.go:289`,
"Only a cluster administrator (kingres_admin) can add a server"), but the REST `addServer` needs only `kingres_ops`. The
leader contacts the address the caller names, signs a cluster certificate for the identity the *new server* announces
(`prep.ServerID`) in `introduce`, and installs it with `/bootstrap/install`, all before any task step runs. Later steps
send the new server every role with its verifier and the databases. The certificate is valid immediately and CP2-01
turns it into administrator rights.

**Scenario.** An ops-level account runs its own `kingresd` on a host the leader can reach (the setup token is printed
locally), calls `POST /servers {"address":"attacker:8091","setupToken":"<local token>"}`. The leader pins nothing (the
account sets no fingerprint), signs and installs the certificate. The attacker's server then forwards
`setRoleClusterRoles` as an administrator, and also receives all SCRAM verifiers for offline cracking.

**Confirmed.** By reading, plus the CP2-01 test for the second half. The first half (that the cluster signs a
certificate for an ops-level caller's server) was not run end to end (no second server).

**Fix.** Require `kingres_admin` for `addServer` (as for the join), or make a newly added server's certificate carry no
forwarding rights until the task is `done`; send role verifiers only after an administrator approved the server.

### CP2-03 (high) — the pin is silently lost on a follower

**Where.** `cp/internal/httpapi/forward.go:129` (only the *header* is forwarded as `Pin`),
`cp/internal/httpapi/handlers_members.go:123-128` (on the leader, a forwarded request uses `pin = f.pin` and never
calls `pinOf` on the body), `cp/internal/httpapi/forward.go:200` and `cp/internal/pki/files.go:231`
(`pinText` = `NormalizeFingerprint`, which returns `""` for anything malformed).

**What happens.** The contract field `expectedFingerprint` (body) of `addServer` is read by `pinOf` only on the server
that receives the request directly. When the request arrives at a follower (the normal case for any client talking to a
non-leader), the body is forwarded but the leader ignores `req.ExpectedFingerprint`; only the header
`X-Kingres-Pin-Sha256` survives, and a malformed header is not rejected (the follower never validates it, the leader
normalizes it to empty). In both cases `AddServer` runs with `pin == ""`, i.e. trust on first use, while the audit
detail says `fingerprintPinned: false`. The administrator who pinned believes the first contact is authenticated.

**Confirmed (test).** A spy `Members` records the pin: direct on the leader, body pin: `aabbcc...` (kept); via follower,
body pin: `""`; via follower, header pin: kept; via follower, malformed header pin: `""` and HTTP 202.

**Fix.** Validate the pin on the receiving server (so a malformed one is 400 everywhere) and forward the normalized
value taken from the body or the header; on the leader use the forwarded value for both sources. Add a test that
`addServer` through a follower with a body pin reaches `AddServer` with that pin.

### CP2-04 (high) — certificates and the CRL expire with no renewal

**Where.** `cp/internal/pki/pki.go:38` (`ServerLifetime` one year), `:355` (`NeedsRenewal`, referenced nowhere else:
`grep -rn NeedsRenewal` finds only its definition), `:434` (`NextUpdate: now.Add(30 * 24 * time.Hour)`),
`cp/internal/cluster/member.go:191-209` (`PublishLocalCRL`, called only from `membership/add.go:497` and `:711`),
`cp/internal/instance/render.go:285-289,411` (`ssl_crl_file`, `sslcrl` in `kingres_shard.node_conninfo` with
`sslmode=verify-full`).

**What happens.** Every server certificate (and the internal API's mutual TLS, the node connections of the sharding
extension and `ssl_crl_file`) stops working one year after issue; nothing renews it (the README says the cluster "keeps
running on its existing certificates until they expire"). Independently, the CRL written at the last membership event is
valid for 30 days and nothing re-issues it. OpenSSL, which PostgreSQL uses with CRL checking, rejects a CRL past its
`nextUpdate`, so inter-node PostgreSQL connections are expected to fail 30 days after the last add or remove. That part
was not run (no PostgreSQL here); it is the documented OpenSSL behaviour.

**Scenario.** A three-server cluster that is left alone for 31 days: the sharding extension's node connections start
failing TLS verification on every server at once. On day 365 the internal API stops answering every peer.

**Fix.** Re-issue the CRL on a timer well inside its validity (and set `NextUpdate` generously), renew server
certificates when `NeedsRenewal` (on the CA holder, with a task and an alert), and add an alert kind for "certificate
expires in N days".

### CP2-05 (medium) — administrator password sent before the fingerprint is checked

**Where.** `cp/internal/cluster/join.go:144-190` (`stepJoinIntroduce`), `:99-125`, `cp/internal/peerclient` `BootstrapCall`.

**What happens.** With no `expectedFingerprint` the joining server connects over TLS that accepts any certificate
(trust on first use), sends the administrator's user name and password in `POST /bootstrap/join`, and only then records
the fingerprint in the task detail ("first use, not verified; compare it with the fingerprint shown on the existing
server"). A man in the middle on the path to the address typed by the operator receives the administrator's cluster
password; the later comparison cannot undo that. The setup token of the add direction has the same property (the token
goes to whoever answers), but that is a one-time local secret; here it is the standing password of `kingres_admin`.

**Confirmed.** By reading only.

**Fix.** Make the pin mandatory for the password-carrying call, or run a first call that only records the fingerprint and
make the operator confirm it (the task pauses) before the password is sent.

### CP2-06 (medium) — lease clocks and no self-fencing

**Where.** `cp/internal/task/pgstore.go:88-99` (`Claim`: `lease_expires_at <= $3`, with `$3` = the claimer's `time.Now()`),
`:101-128`, `cp/internal/task/task.go:449-470` (`renewLoop`: a failed renewal other than "lease lost" is only logged),
`cp/internal/task/task.go:335-420` (`run`).

**What happens.** The lease expiry is written and compared with the Go clock of whichever server claims, never with the
database clock. A new leader whose clock is ahead of the old one by more than the remaining lease claims a task that the
old leader is still running. Separately, a leader that can no longer renew (the store is unreachable, or the process was
paused for longer than the lease) keeps executing the current step; there is no local expiry time after which the step
context is cancelled, so the step can run after another server took over.

**Confirmed (test).** Two engines on one store, engine B's clock five minutes ahead, lease 30 s: the same step was
started twice while A's lease was fresh. (The in-memory store was used; the SQL store has the same semantics by
reading.) `NonIdempotent` steps are only protected when the new holder sees the "running" mark; in this race it does and
fails the task with `step_interrupted` while the first holder completes the effect.

**Fix.** Use the database's `now()` in `Claim`, `Renew` and the expiry test; give the run context a deadline equal to the
last successful renewal plus the lease minus a margin so that a leader that cannot renew stops its step; carry a lease
epoch (fencing token) in `SetStep` and in remote calls.

### CP2-07 (medium) — revocation of access reaches unreachable servers late

**Where.** `cp/internal/ops/fanout.go:290-330` (`replicate`: a server that cannot be reached gets a waiting task) and
`:356-368` (`roleChanged`: "it re-checks every role within a few seconds (auth.Revalidator), so the worst case is that
bound"), `cp/internal/auth/revalidate.go:63-95` (the check asks the *local* PostgreSQL).

**What happens.** Roles live in each server's own PostgreSQL and are copied by `role.sync`/`role.drop` calls. The
revalidator asks the local instance, so on a server that the leader cannot reach (partition, down, instance stopped) the
role still exists with its old attributes, memberships, cluster roles and password until the replication task finally
gets through. The in-process sessions there are not ended (the `role.changed` call fails the same way). The stated bound
of a few seconds only holds for servers that answered.

**Scenario.** An administrator is dismissed and `deleteRole` runs while a follower is partitioned from the leader. The
person can still sign in to that follower with the old password and use any operation that is not forwarded (the
workbench `executeQuery`, reads, `this-server` operations) for as long as the partition lasts; forwarded mutations are
refused because the leader's PostgreSQL no longer has the role.

**Confirmed.** By reading only.

**Fix.** Make the revoking operation report which servers have not applied it (the task already exists) and expose that in
the response and as an alert; have followers refuse sign-in and session use when they have not heard from the leader for
longer than a bound that the leader announces with the role revision.

### CP2-08 (medium) — verification and digests cover one shard group

**Where.** `cp/internal/ops/ledger_verifications.go:68-80` (`localGroup`), `cp/internal/ops/ledger.go:68-73` (`toDigest`:
one chain, no `AggregateHash`), `:174-215` (`stepVerifyLedger`), `cp/internal/ops/ledger_verifications.go` `toVerification`.

**What happens.** The digest list, `generateLedgerDigest` and the verification records read the chain of the shard group
of the server that runs the request (the leader for the mutating ones). A database with several shard groups returns a
digest with a single entry in `chains` and `aggregateHash: null` (the contract says the aggregate is the Merkle root over
the chain heads "for a sharded database"), and a verification that checked only that chain is answered
`state: passed`, `scope: full`. The README ("Not done: records of other shard groups") says so, the response does not:
a client or auditor cannot see from the answer that the other groups were never checked, and a stored digest does not
anchor them. In addition `stepVerifyLedger` ends successfully without creating any record when there is nothing new
(`ledger.go:199`), so a task `done` does not prove that a verification record exists.

**Confirmed.** By reading only (no PostgreSQL).

**Fix.** Until all groups are covered, answer `422 unsupported_operation` (or a field such as `partial: true` and the
list of unchecked groups) for a database that has more than one shard group; never report `passed` for a part.

### CP2-09 (medium) — one account can lock everybody out of sign-in

**Where.** `cp/internal/auth/session.go:106` (`len(s.sessions) >= s.max` -> `ErrTooManySessions`), default
`cp/internal/config/config.go` `MaxSessions: 10000`, `cp/internal/httpapi/handlers_core.go:217-290` (`login`, up to two
sessions per call).

**What happens.** The cap is global; there is no per-user limit and sessions live for the absolute TTL (8 h). The login
rate limit is 10 per minute per address and per user name. An account with any cluster role (even `kingres_stats`), or
anyone holding one leaked credential, signs in repeatedly with `issueToken: true` (two sessions per call) and fills the
store in minutes from a few addresses; after that every sign-in, administrators included, gets `503` until the sessions
expire or the process restarts (the store is in memory, so an operator must restart `kingresd`).

**Confirmed.** By reading only.

**Fix.** Cap sessions per user (for example 20) and evict the oldest session of that user first; keep the global cap as a
backstop.

### CP2-10 (medium) — limiter tables turn into a lock-out

**Where.** `cp/internal/auth/ratelimit.go:27,48-60` (`maxKeys: 50000`; when full a new key is refused), used by
`publicLimiter` (all operations without a session, including `login`, keyed by address), `loginIP`, `loginUser`
(`cp/internal/httpapi/server.go:160-163`) and the `join-user:` limiter in `cp/internal/membership/handle.go:270`.

**What happens.** An attacker that makes one request from each of 50000 distinct source addresses within a minute (a /64
IPv6 prefix is enough) fills the address table; from then on every request without a session from any new address
(sign-in, `healthz`, `readyz`, setup state) is answered `429` for the window, and the same attacker can keep it full.
The user-name table behaves the same for new user names (50000 names at ten attempts per minute per address needs many
addresses, so this is harder). A load-balancer health check from a new address is also refused.

**Confirmed (test).** After 50000 distinct keys, a new address is refused with a one-minute wait, and `root_admin` is
refused when the user table is full; both recover after the window.

**Fix.** Do not refuse when full; evict the oldest keys, or key IPv6 clients by /64, and exempt `healthz`/`readyz` from
the public limiter.

### CP2-11 (medium) — a truncated DML result is rolled back but reported as success

**Where.** `cp/internal/ops/query.go:85` (deferred rollback), `:106-110` and `:121-125` (when `rowLimit` or the byte budget
is reached the code sets `Truncated`, cancels, and returns without committing), `:138-145` (`commandTag` forced to
`"SELECT n"`).

**What happens.** `UPDATE t SET x = 1 RETURNING *` on 5000 rows with the default `rowLimit` 1000 changes nothing (the
transaction is abandoned) and is answered `200 {"truncated": true, "commandTag": "SELECT 1000", ...}`. The caller sees a
successful write, with no hint that it was undone. The audit event, written for every executed statement, also says it
succeeded.

**Confirmed.** By reading only.

**Fix.** For a statement that is not a plain read (`CommandTag` not `SELECT`), either refuse truncation (fail with 422 and
roll back, naming the reason) or keep reading the rows (discarding them) so that the statement completes and commits.

### CP2-12 (medium) — `timeoutMs` does not do what the contract says

**Where.** `cp/internal/httpapi/guard.go:76` (the request context has `RequestTimeout`, default 30 s in
`cp/internal/config/config.go:243`), `cp/internal/ops/query.go:79` (the statement context is derived from it),
`cp/internal/ops/ops.go:179-193` (`PGProblem` maps a context deadline to `503`). Contract: `QueryRequest.timeoutMs` 100..300000,
default 30000, "statement timeout"; `executeQuery` description: statements that fail return 422 with code `sql_error`.

**What happens.** The 30 s request deadline fires before `statement_timeout` (30 s) plus the 2 s grace, so the
*default* `timeoutMs` ends as `503 service_unavailable` ("The operation timed out", `Retry-After: 5`) and any value above
about 28 s is ineffective. The PostgreSQL cancellation (`57014`) is mapped to 422 only when it wins the race.

**Confirmed.** By reading only.

**Fix.** Give `executeQuery` its own context deadline of `timeoutMs` plus a grace period (raise `WriteTimeout`
accordingly for that route), and map `context.DeadlineExceeded` of a statement to `422 sql_error` with `sqlState 57014`.

### CP2-13 (medium) — the audit log is incomplete when read from a follower

**Where.** `cp/internal/httpapi/forward.go:47-55` (`leaderBoundReads` does not contain `listAuditEvents`),
`cp/internal/httpapi/guard.go:72-76` and `:329-366` (the leader writes the event of a forwarded operation, the
follower writes none), `cp/internal/audit/audit.go:111-150` (`Append`: a file per server), `cp/internal/httpapi/guard.go:385-388`
(an audit write error is only logged).

**What happens.** Each server answers `GET /audit` from its own `audit.jsonl`. Every administrative action done through a
follower is audited only on the leader, so an administrator reading the audit on any other server sees sign-ins but none
of the role, grant, database, network or membership changes; after a leader change the history stays on the old
leader's disk. The task engine's own events (for example `addServerDone`) are written by the leader as well. Separately,
the audit write happens after the operation: when the disk is full or the file cannot be written, the operation stands
and only a log line says so, which contradicts "every execution is written to the audit log" (contract text of
`executeQuery`).

**Confirmed.** `TestMutationOnAFollowerIsForwardedAndAuditedOnce` itself asserts that the follower audits nothing; the
read path was confirmed by reading.

**Fix.** Make `listAuditEvents` leader-bound (or merge the files of all servers) and replicate the audit to the new
leader on a change; for state-changing operations write an "intent" record before the action and refuse the action if
that write fails.

### CP2-14 (medium) — removal order and a missing CA key

**Where.** `cp/internal/membership/remove.go:51-60` (steps: `Stop and delete the instance` is marked `Irreversible`
and comes before `Revoke the certificate`), `:155-176` (`stepRemoveRevoke` returns the error of `m.Svc.CA()` when the
leader does not hold `ca.key`), `cp/internal/membership/add.go:335-350` (`discardPending` silently skips the revocation
when the CA is not held), `:742-775` (`addFailed`), `:357-377` (`SweepAbandoned`), `cp/internal/membership/leave.go:166`.

**What happens.** The CA key is held by the first server only (README, "What has to move with the manager"), while the
leader is whoever holds the primary of shard group 0. When they differ, `removeServer` runs the reset of the removed server
(irreversible) and then fails at the revocation step as `step_failed, retryable: true`; a failed task is not resumed, and
a new `removeServer` for the same id is refused (`removing` state, server unknown to the catalog afterwards),
so the server is gone, its certificate stays valid for up to a year (CP2-01 applies to it) and there is no operator
action in the API that repairs it. `discardPending` deletes the pending row without revoking when the CA is absent
(`if ca, err := ...; err == nil && ...`), so a certificate signed by the CA holder for an abandoned join is neither
revoked nor remembered. A pending server whose add task failed after `registering` was set is never swept
(`SweepAbandoned` skips `Registering`) and keeps its valid certificate.

**Confirmed.** By reading only. The limitation itself is documented; its consequences for removal are not.

**Fix.** Check `HoldsCA()` before starting `addServer`/`removeServer`/`leaveCluster` and refuse with a clear problem;
revoke before the irreversible step; record a revocation as a pending obligation (system database row) that any holder of
the CA completes.

### CP2-15 (low) — workbench slots

`cp/internal/ops/query.go:64-70`, `:236-239` (`maxWorkbench = 4`, one global channel, `503` when full). A single
`kingres_readonly` account can run four `select pg_sleep(300)` statements (timeoutMs is capped as in CP2-12, so about
30 s each, repeated) and keeps every other user's workbench at `503`. Fix: a per-user limit (one or two) below the
global one.

### CP2-16 (low) — audit file scan

`cp/internal/audit/audit.go:151-170` (`Query` collects every matching event of the file in memory, then trims to
`Limit+1`), `:201-225` (`scan` reads the whole file each time). The file grows without bound and without rotation;
anonymous requests that reach PostgreSQL (`login` attempts within the per-address limit) are audited, so growth is
attacker-influenced. A year of busy use makes `listAuditEvents` slow and memory-hungry for the administrator. Fix: scan
backwards from the end, stop at `Limit+1`, and rotate with an index.

### CP2-17 (low) — log directory

`cp/cmd/kingresd/main.go:215` and `:103` of `cmd/kingresd/internal.go` fix the log directory at
`instances/1/pgdata/log`, while `updateThisServerSettings` (`cp/internal/localsettings/localsettings.go:306-380`, rendered
by `instance/render.go:226-231`) lets an administrator move `log_directory`. After the move (and a restart) `GET /logs`
and `GET /this-server/logs` read the old directory and show nothing new, with no error. Fix: read the directory from the
managed settings (`Manager.LogDir` exists and ignores them too).

### CP2-18 (low) — revocations are not durable

`cp/internal/pki/pki.go:381-399` (`saveLocked`: `os.WriteFile` to a temp file and `os.Rename`, no `fsync` of the file or
the directory), `cp/internal/pki/files.go:43-65` (`WriteFile`, same). After a power loss the rename can be lost or the
file empty, which un-revokes a certificate. Fix: `Sync` the file and the directory.

### CP2-19 (low) — `LastGood`

`cp/internal/auth/revalidate.go:63-95` (`Roles`), `:97-108` (`Changed`). `Roles` stores `good[username]` unconditionally, while `Changed` clears
`good` and bumps `epoch`; a check that was in flight when `Changed` ran writes the old roles back, and `LastGood` can then
serve them for up to the bound. `cp/internal/httpapi/handlers_instance.go:240-262` additionally falls back to the roles
the session had at sign-in when no check exists and the session is younger than `DefaultStaleRolesMaxAge` (one hour): that
covers the case "role of another user changed by a group membership while this server's instance was stopped". Both are
limited to `startThisServerInstance` and to one hour, and `LastGood` cannot be used for anything else (verified:
`grep LastGood` shows the single caller), so the abuse available is "start the local instance". Fix: store `good` only
when the epoch is unchanged, and prefer a refusal over the sign-in roles.

### CP2-20 (low) — peer task calls

`cp/cmd/kingresd/internal.go:243` passes only the body to `HandleTaskCall` (the verified peer id is dropped);
`cp/internal/ops/taskrecorder.go:225-268`. Any peer can record a running `instance.*` task for any instance subject
(blocking the real start/stop/restart with `operation_in_progress` for the 15-minute record lease,
`task/record.go` `RecordLease`) and settle any task of those kinds. Settling other kinds is refused. Fix: accept
`instanceId`s of the calling server only.

### CP2-21 (note) — plaintext and public information

`cp/internal/config/config.go:344-372` accepts any `listen` address without TLS; the session cookie is always `Secure`, so
the panel then works only on localhost, but bearer tokens and passwords of API clients cross the network in clear text.
Refuse (or loudly warn about) a non-loopback listener without TLS unless an explicit flag is set. `getNodeState`
(`httpapi/handlers_core.go:128`) and `getReadiness` tell an unauthenticated caller the host name, versions, node state and
whether PostgreSQL is reachable (public by contract).

### CP2-22 (note) — stop is settled before the stop

`cp/internal/ops/instancerun.go:180-215` records the task as `done` first (the row lives in the database that is about
to stop) and corrects it to `failed` if the stop fails. A crash of `kingresd` between the two leaves a `done` task and a
running instance; the design choice is understandable but should be in the README next to the task description.

## Examined and found sound

- **DSN and SQL construction.** `pgconninfo` is the only connection-string builder (`ParseConfig("")` plus struct fields
  in `cluster/proxy.go:131`; `NodeConninfo` goes through it). `sqlx` identifiers and literals are quoted (E-string when a
  backslash is present); all statements in `ops/roles.go`, `network.go`, `ledger*.go`, `fanout.go`, `membership/*` use the
  builder or bind parameters. No injection found in the files read.
- **pg_hba / pg_ident / managed configuration.** `hbaName` refuses quotes, commas, `#`, backslash, control characters and
  a leading `@` or `+`; addresses are re-rendered from a parsed prefix; map names must match a plain pattern;
  `confValue` doubles backslashes and quotes; `forbiddenExtra` blocks file and command settings; `validateConfPath`
  refuses `..` and non-clean paths; `log_directory` goes through it. `local all all peer map=...` plus the ident file
  restricts local trust to the `kingresd` OS user.
- **Sessions, CSRF, cookies.** 32-byte random credentials stored as SHA-256; cookie `HttpOnly`, `Secure`,
  `SameSite=Strict`, `Path=/`; CSRF token compared in constant time; bearer and cookie kinds not interchangeable;
  `Sec-Fetch-Site: cross-site` refused on mutating operations; the role of every operation comes from the contract and
  `TestRoleMatrix` enforces it for all 86 operations and four roles; the eight unimplemented operations answer a uniform
  `unsupported_operation` after the guard.
- **Setup and unauthenticated surface.** Setup token: random, constant-time check, per-address failure limiter, loopback
  gate while uninitialized, refused afterwards. Without a session only `healthz`, `readyz`, `getNodeState`, `login`,
  the three setup operations, `/metrics` (token) and the static panel are reachable; `/metrics` needs the scrape token
  or a current `kingres_stats` token session.
- **Static files and routing.** The panel is served from an embedded file system with `path.Clean`; `/api` and `/api/*`
  never fall through to the panel; a path with an extension that does not exist answers 404 instead of `index.html`;
  Go's mux cleans `..` and `//`. No traversal found.
- **Headers and limits.** CSP without inline sources, `frame-ancestors 'none'`, `nosniff`, `no-referrer`, COOP/CORP,
  HSTS only when TLS is configured (not from a request header), `Cache-Control: no-store` by default; JSON bodies limited
  (1 MiB default) with unknown fields refused; server timeouts (header 10 s, read 30 s, write 60 s, idle 120 s) and
  header size limit set on both listeners; X-Request-Id restricted to a safe alphabet; panic recovery does not leak the
  stack to the client.
- **Internal API.** TLS 1.3, certificate verified against the CA with client-auth usage and revocation; fixed call
  table (unknown path 404), version header checked first, leader checks for `LeaderOnly`/`ToLeader` calls, body limits,
  `exec` accepts one statement with bounded result and logs only length and hash, forwarding rebuilds the URL
  structurally and checks the operation id against the contract, path parameter count and query string.
- **Key and file handling.** `ca.key`, `server.key`, `bootstrap.key`, the service password file, `revoked.json`,
  audit file, local settings and `peers.json` are 0600, the `pki` and instance directories 0700; the PKI helper writes
  through a temporary file and renames; the CA is created with an exclusive create and a refusal if one exists;
  certificates are only 0644; CSRs are checked for key type, signature, common name and names before signing.
- **Task engine basics.** One unfinished task per subject (unique index), the holder is checked in every write
  (`SetStep`, `Finish`, `Renew`), `NonIdempotent` steps are not repeated (`step_interrupted`), secrets are kept in
  memory only, `OnFail` cleanup exists for `server.add`, instance tasks have a 15-minute record lease and an
  `interrupted` definition so that a crash does not leave them running forever.
- **Concurrency.** The nine packages listed above pass `go test -race`; sessions, limiter, revalidator, leader resolver,
  audit sink and peer client use mutexes consistently; the peer client has a bounded connection pool per server and
  bounded response reads (64 MiB).
- **Workbench basics.** One statement per request (extended protocol with `QueryExecModeExec`), runs on a connection as
  the signed-in role through a peer-authenticated socket, refuses superuser/replication/bypass-RLS roles and members of
  the file/program/log predefined roles, per-request transaction with `set_config('statement_timeout', $1, true)`
  as a bound parameter, the statement text is not written to the audit file (length and hash only).
- **Audit coverage of the contract.** All mutating operations except `previewRebalancePlan`, `createInclusionProof` and
  `checkSetupToken` (which change nothing) are audit actions; refused (403, CSRF, validation) requests of authenticated
  callers are audited with the actor; rejected setup tokens are audited. Unauthenticated 401s, cross-site refusals and
  rate-limited logins are deliberately not (stated in the code).

## Unconfirmed (what would confirm each)

- **Digest attribution.** `generatedBy` of a digest is read from `kingres.ledger_digest.generated_by`
  (`ops/ledger.go:65`) and `GenerateDigest` runs as the service role, so the value is probably `kingresd`, not the
  requesting role or `system` as the contract says (the verification mapping does translate the service role to
  `system`, digests do not). Needs a run of `generateLedgerDigest` against PostgreSQL with kingres_ledger 0.2.
- **CRL expiry behaviour.** That PostgreSQL/libpq reject an expired CRL on inter-node connections (CP2-04) is the
  documented OpenSSL behaviour but was not exercised; confirm with a cluster whose `revoked.crl` is regenerated with a
  `NextUpdate` in the past.
- **One huge value.** `select repeat('x', 800000000)` through the workbench (CP-04, partial): expected to make
  `kingresd` allocate the whole value before the 1 MiB check. Needs PostgreSQL.
- **Case-insensitive names.** Server identity is compared as an exact string (`l != peer`) while certificate host
  matching is case-insensitive. A member added as `Node1` next to an existing `node1` could answer a connection meant for
  `node1` if an attacker also controls the network path or DNS. Needs two servers and a certificate for the variant.
- **Internal exec has no statement timeout.** `execLocal` runs as the superuser with only the request context, which
  ends when the leader disconnects. Only the leader can call it; a leader-side bug could leave statements running.
- **Leader change under a pause.** The behaviour of `kingres_shard`'s primary election with a paused old leader (ADR 0018)
  and its interplay with CP2-06 was not tested; the fencing the peers apply is "the caller is the leader in my own
  cached view" (`leaderOf`, cache of a few seconds, and the last known leader is used while the local instance is stopped).
- **Ledger byte-exactness.** Digest download, inclusion proof and the verifier's input were not compared byte for byte.
