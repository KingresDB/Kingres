## Findings

### P12R-01 (medium): the P10F-02 fix makes `split_bucket(..., verify => 'full')` fail for tables with a column that has no equality operator

File: `contrib/kingres_shard/kingres_shard--0.7--0.8.sql` line 1867 (and `kingres_shard--0.8.sql` line 13305), function
`internal_split_switch`: `ON CONFLICT (...) DO UPDATE SET ... WHERE (c.a, c.b) IS DISTINCT FROM (EXCLUDED.a, EXCLUDED.b)`.

Scenario: a distributed table has a `json`, `xml`, `point`, `box` or similar column (no `=` operator). `split_bucket` with verify
`full` ran before the fix; after it the statement fails with `operator does not exist: json = json`, every attempt, and the split
is undone after the whole copy. Reproduced on PostgreSQL 18 with
`INSERT INTO t AS c (id,j,x) SELECT ... ON CONFLICT (id) DO UPDATE SET j=excluded.j, x=excluded.x WHERE (c.j, c.x) IS DISTINCT FROM (excluded.j, excluded.x)`
on a table with `j json`: `ERROR: operator does not exist: json = json`.

Fix: compare the columns as text for types without an equality operator, or compare whole rows with `record_image_ne`
(`c IS DISTINCT FROM EXCLUDED` does not help for json either, so use `c::text IS DISTINCT FROM EXCLUDED::text` only for those
columns), or fall back to the unconditional `DO UPDATE` when any non-key column type has no default btree/hash opclass (look it up
in `pg_type.typisdefined` / `pg_amop`, or with `pg_catalog.pg_operator` for `=`). Test: in t/204 add a `json` column to the
table and run the verify `full` case; it must finish and still repair the two wrong values.

### P12R-02 (medium): a merge with `ext-partfix` brings the `not_available_yet` partition blocker back in a fresh 0.8 install

Files: `contrib/kingres_shard/kingres_shard--0.8.sql` lines 6275, 7030, 7037; `mk-install-script.sh`.

`kingres_shard--0.8.sql` is generated by `mk-install-script.sh` from `kingres_shard--0.7.sql` (from its `\echo` line on) plus the
`0.7--0.8` script. Commit 7cfef346e0 on `ext-partfix` changes `0.7.sql` and `0.6--0.7.sql` only. `0.8.sql` still has the
old body of `table_change_report` (the unconditional `'blocker', 'not_available_yet'` at lines 7030 and 7037 and the `not_available_yet`
at 6275, which are the same text as in the old `0.7.sql`). After a merge, git reports no conflict (the branch does not touch `0.8.sql`),
so the merged tree has: an upgrade 0.6 -> 0.7 -> 0.8 with the fix, and `CREATE EXTENSION kingres_shard` (version 0.8) without it.
`kingres_shard--0.7--0.8.sql` itself does not redefine `table_change_report` (checked: no match), so the upgrade script is not the
problem; the generated file is. I checked that the committed `0.8.sql` equals the output of the generator on this branch today.

Fix: after the merge run `sh mk-install-script.sh` in `contrib/kingres_shard` and commit the result; add to the gate a step that
runs the generator and fails on a diff (`git diff --exit-code kingres_shard--0.8.sql`). Test: t/199 (from `ext-partfix`) must run
against a fresh install of 0.8 and against the upgraded one; the `upgrade` regress test should compare the bodies of the
functions (`prosrc` hashes), not only the objects, if it does not already.

### P12R-03 (medium): the lazy lookup of dist_schema uses a primary key OID that is not refreshed when the index is replaced; and a missing index silently means "not distributed"

File: `contrib/kingres_shard/src/catalog.c` lines 759-760 (OIDs read at load), 1151 and 1220 (guards), 1227 (use).

The cache stores the OIDs of `dist_table_pkey` and `dist_schema_pkey` when it is loaded and reuses them until the next load.
`catalog_inval_callback` drops the cache only for the relcache entries of node, colocation, dist_table, bucket_map, map_version and
local_node; `dist_schema` is not in that list (its changes drop the cache through the trigger on map_version).
Scenario 1: `REINDEX (CONCURRENTLY) TABLE kingres.dist_schema` (or `REINDEX DATABASE CONCURRENTLY`) gives `dist_schema_pkey` a new
OID and drops the old one without a write to the catalog table, so no trigger fires and the cache keeps the old OID. Every lookup
of a distributed schema in every backend then fails with "could not open relation with OID ..." (an error on all statements on
distributed schemas) until some other catalog change reloads the cache. (Not run; follows from the code.) For `dist_table` the
heap relcache invalidation of the same operation reloads the cache, so only the schema index is exposed.
Scenario 2: if the index is missing or has another name (a restore that renamed it, a manual DROP of the constraint),
`!OidIsValid(ks.dist_table_pk)` returns NULL, so a schema table is silently treated as a local table: wrong answers, no error.

Fix: take the index from the opened relation instead of from a stored name and OID: after `table_open`, use
`RelationGetPrimaryKeyIndex(rel)` (PG18 and PG19 both have it; if it is `InvalidOid`, scan the heap with `indexOK = false`, which
is correct and only slower). Remove `dist_table_pk` and `dist_schema_pk` from `ks`. Test: in t/247 run `REINDEX (CONCURRENTLY) TABLE
kingres.dist_schema` and `kingres.dist_table` and then a statement on a schema table from a backend that had the cache loaded;
second case: `ALTER INDEX kingres.dist_table_pkey RENAME TO x` and the same statement.

### P12R-04 (low): `add_node` with no distributed schema left skips the reconciliation and leaves staged schemas and progress rows on the new node

File: `contrib/kingres_shard/src/node_admin.c` line 926 (`if (names == NIL) return 0;`) and lines 1588/1609 (`staged_schemas > 0`).

Scenario: call 1 stages schema `s1` on the new node and fails later (for example the registration is cancelled). Before call 2 the
last distributed schema of the cluster is made local (`undistribute_schema`). Call 2 sees no schema, returns before connecting to
the node, so the node is registered with the old schema `s1`, its tables and its `add_node_progress` row still on it: an orphan
local schema on a cluster node, and a progress row that nothing removes (the final `DELETE` runs only when `staged_schemas > 0`).
Later, if a schema of that name is distributed again, `CREATE SCHEMA` for it fails on that node or the old digest is taken as done.
With a non-empty list the code does handle this (it drops what changed or went away), so the hole is only the empty list.
Fix: always connect and read `add_node_progress` when the new node has the table (the extension is made first); drop what the
progress rows name that is no longer in the list; run the final `DELETE FROM add_node_progress` whenever the table exists. Test:
extend t/248 section C: undistribute every schema between the calls and check that the new node has no `s*` schema and an empty
progress table after the second call.

### P12R-05 (low): a missing role is classified as a "dependency" and the schema is deferred to the last transaction; the role check runs after the batches

File: `contrib/kingres_shard/src/node_admin.c` line 842 (`stage_error_is_dependency`: `ERRCODE_UNDEFINED_OBJECT`) and line 1486
(`check_acl_roles_on_node` is called after `stage_schemas_on_node`, which is called at line 1482).

`CREATE SCHEMA ... AUTHORIZATION r` or `ALTER FUNCTION ... OWNER TO r` with a role that does not exist on the new node raises 42704
(undefined_object), which the staging treats like "reads a reference table that is not there yet": the schema is rolled back to
the savepoint and its script is run again in the last transaction, where it fails with the generic error of `kingres_shard_exec`
(no hint that the batches are kept) after every batch and after the reference tables were copied. `ACL_ROLES_SQL` covers owners
of tables and schemas and grantees, not the owners of functions, sequences, types, views or roles named in default privileges, so
the role pre-check does not always catch them either.
Fix: run `check_acl_roles_on_node` (extended with the roles of the schema structure) before the staging; narrow the dependency
classes to 42P01 (undefined_table) and 3F000 and to 42883/42704 only when the message names a relation or function (or
check for the role first and treat 42704 as a dependency only if it is not a role). Test: t/248 with a function owned by a role that
the new node lacks: the call must fail before the first batch with the role message.

### P12R-06 (low): the per-table invalidation cannot see rows that the transaction deleted (already so before step 12)

File: `contrib/kingres_shard/src/catalog.c` `written_ids` (line 1507 on), `bump_invalidate_changed` (line 1541).

The pass looks at tuples whose inserting transaction is the current one; a DELETE leaves only a tuple that is no longer visible, so
`internal_unregister_schema_table`, `internal_unregister_schema`, `undistribute_table` and a pure DELETE of a bucket map row
invalidate no table. The old code (SELECT of dist_table joined with pg_class after the delete) had the same hole, so this is not a
regression; the cache itself is dropped (the trigger always invalidates map_version, which every backend reacts to), only
plans are affected. I could not construct a stale plan: the paths I looked at (shells dropped on other nodes, the table
rebuilt or altered on the owner) invalidate the relation by other means. A fix that does not depend on that: scan with
`SnapshotAny` and also take tuples whose `xmax` is the current transaction and that were deleted (not locked: check
`HEAP_XMAX_IS_LOCKED_ONLY`), or use a transition table (`REFERENCING OLD TABLE`) on the statement triggers. Test: a prepared generic
plan on a schema table in a session on the owner, `undistribute_schema` on the map node, then execute the plan.

### P12R-07 (low): notes that need no change now

- `md5()` is used for the digests (`internal_add_node_schemas`): it fails on a server with a FIPS-mode OpenSSL. `sha256` of the text
  (`pg_catalog.sha256(convert_to(script, 'UTF8'))`) has the same cost. 40 characters were reserved in the hash entry for it: a hex
  sha256 needs 65.
- `bump_invalidate_changed` reads each of the catalog tables whole for every statement that writes it, so a transaction that makes
  N schemas (N statements) costs O(N * rows). It is correct; a loop of 2000 `CREATE SCHEMA` in one transaction is quadratic. Consider
  remembering the highest command id already handled in the transaction.
- `kingres_shard.catalog_incremental` is `PGC_USERSET`; any role can turn it off for its own session, which only costs it
  invalidations (it also floods the other backends with relcache messages). `PGC_SUSET` would be calmer.

## What I checked and found sound

Cache (step 12 b):
- The whole cache (the backend's own and every other backend's) is still dropped by the relcache invalidation of `map_version`, which
  the trigger sends unconditionally; the incremental part concerns only the relcache invalidations of distributed tables
  (cached plans). So no write can leave a stale cache entry in the sense of the hash tables; negative entries live in the
  cache that is dropped with it (a "no" that becomes a "yes" needs a catalog write, which drops the cache).
- Lazy lookups: HASH_ENTER never moves other entries; pointers returned stay valid; the entries are made in the context of the
  cache that was loaded, retired contexts live until the end of the transaction, so an invalidation in the middle of a lookup
  (`table_open` accepts messages) only marks the cache as invalid and the entry goes into the old cache. `memset` after
  HASH_ENTER restores `relid` / `nsp`. Lookups return NULL while loading and for a `KsCatalog` that is not the cached one.
  `GetLatestSnapshot` is used like `catscan_begin` (parallel mode uses the active snapshot).
- `written_ids`: an updated row (HOT or not) shows as a new tuple with this transaction as xmin, subtransactions are covered by
  `TransactionIdIsCurrentTransactionId`, an aborted subtransaction leaves invisible tuples and its invalidation messages are
  discarded with it; TRUNCATE and every table other than dist_table, colocation, bucket_map and dist_schema fall back to the old
  "all tables". The first read-write SPI statement of the trigger (the update of map_version) advances the command id, so the
  snapshot of the scan sees the rows of the statement. 2PC: messages go out at COMMIT PREPARED as for every invalidation.
  A table written under `DISABLE TRIGGER` (the upgrade script updates for `max_modulus` and `modulus`) is not a concern: those
  updates change no placement.
- 9a4e4cb329 (one statement per table in `internal_apply_catalog`): the delete statements come first (they only invalidate through
  the map_version bump), then one INSERT per table; each fires the statement trigger once and `written_ids` finds every inserted
  row, because they all carry this transaction as inserter. t/247 B2 counts the firings.
- Colocation group changes, bucket moves and splits (update of `bucket_map` / `colocation`), `internal_set_schema_group`,
  `ship_functions` changes (update of `dist_schema`) and schema rename / `SET SCHEMA` (a `dist_table` insert of the relation) all name
  the right tables. A reused OID cannot hit a stale entry: the row of the dropped table goes with the drop trigger and the cache is
  dropped.
- No `PG_VERSION_NUM` / `PG_MAJORVERSION` in the diff; no new source file; both new TAP tests and the SQL carry the SPDX header; the
  diff is ASCII. The row-moving distributed scan is untouched.

add_node (step 12 a):
- A half-made node cannot receive rows or be seen: the schemas are made before `kingres.node` has the node (the registration is the
  last transaction), the control session of the staging does not go through the extension's hooks (the node has no `local_node` row),
  and the final check of the progress rows against `pg_namespace` runs in the registration transaction before the catalog is applied
  (t/248 F). `add_node` takes the catalog lock (ExclusiveLock on `map_version`) before it reads the schemas and holds it to the end;
  every DDL of a distributed schema and every catalog write propagates from the map group primary under the same lock (or blocks
  on the trigger's update of `map_version`), so no change of a schema can slip between the digest and the registration; a second
  `add_node` (same or other node) waits and then sees the registered node or runs alone.
- The digest is of the whole script of `internal_schema_structure` plus the schema statement (columns, indexes, constraints,
  sequences, owners, grants, comments, functions, triggers, views), so a change between two calls makes the schema be dropped on
  the new node (only if the progress row says an earlier call made it) and made again (t/248 C, D).
- Removing the copy of schema tables as reference tables: the old path also copied the rows of every schema table to the new node
  as if it were a reference table (the `column == NULL` branch); the shells now come from the staged structure, foreign keys and
  privileges are in it, and the catalog apply finds each table by name (t/248 E: reads and writes from the new node reach the owner).
- Memory: the lists of the staging live in the context of the caller (the outer SPI context, alive until the body ends) and
  the late scripts in the context of the call, taken before the outer `SPI_connect`; the hashes are in the caller's context; the
  `PG_TRY` block modifies no variable that the `PG_CATCH` block reads. The nested `SPI_connect` / `SPI_finish` resets `SPI_processed`
  and `SPI_tuptable` of the outer connection, but the body reads no earlier result after the staging. Only a small leak: the
  `sql` string of each schema is not freed (bounded by the call).
- Savepoint use: after a dependency error `ROLLBACK TO SAVEPOINT` undoes the statements of that schema only; any other error
  ends the call and the connection close rolls the open batch back; closed batches are kept and the call is repeatable.

Upgrade:
- `kingres_shard--0.7--0.8.sql` creates `kingres.add_node_progress` (primary key, revoked from PUBLIC) and
  `internal_catalog_stats` / `internal_add_node_schemas` (revoked from PUBLIC); the two settings are defined in C. It does not
  redefine `table_change_report`. `0.8.sql` is byte-equal to the output of `mk-install-script.sh` (see P12R-02 for the merge).
  The regress expected output lists the new table and settings.
