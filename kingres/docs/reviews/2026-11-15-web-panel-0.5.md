# Independent review of the KingresDB web panel (kingres/web), contract 0.5.0

Date: 2026-11-15. Reviewer: independent (not the author). Second review; the first is
`kingres/docs/reviews/2026-11-14-web-panel.md` (findings W-01 to W-18).

Commit reviewed: `36af22e61f` (branch `kingres-18`). All file and line references are to that commit.

the only file added to the repository is this report.

### W2-01 medium - Start instance targets instance 1 unless the This server page was opened first

Where: `src/api/availability.ts:26` (`instanceId: 1`) and `:55-58` (`rememberInstances`), filled only by
`src/pages/ThisServerPage.vue:46-52` and `src/components/this-server/InstanceActionDialog.vue:24`;
used by `src/components/this-server/SystemDatabaseStopped.vue:54`.

What happens: the stopped-state page starts `availability.instanceId`. That value is the host of the system database
only if, in this page load, the administrator opened This server (or stopped the instance from its dialog). Otherwise
it is the constant `1`. The id cannot be read once the system database is stopped (every authenticated read answers
503), and the page does not show which instance it is about to start.

Scenario: administrator A stops the instance of the system database from the CLI or from another browser; administrator
B has the panel open on Databases. B's next request answers 503 `system_database_stopped`, the page shows "Start
instance", B presses it.

Confirmed: yes. Test against the mock (system-database instance is `#11`): sign in, open `/dashboard`, set the stopped
flag, navigate; the page appears; pressing Start sent `POST /this-server/instances/1/start`.

Fix: persist the host instance id in the query cache or `sessionStorage` (a number, not secret) as soon as any
instance list is read, show "Start instance #N (map group)" on the button, and when the id is unknown ask the
operator to use the machine instead of guessing. Better, ask the contract for a way to start "the instance that hosts
the system database" without an id.

### W2-02 medium - Reload while the system database is stopped drops a valid session

Where: `src/stores/session.ts:57-69` (`restore`: any error ends in `adopt(null)`), `src/router/index.ts` guard
(`session.restore()` before any page).

What happens: the contract says `startThisServerInstance` keeps working "for a sign-in that was valid before the
stop", and that only when no valid session exists must the operator go to the machine. But `getSession` is an
authenticated operation and answers 503 `system_database_stopped` while stopped. A fresh page load calls
`restore()`, gets that 503, and treats it as "not signed in": the user lands on `/login`, where signing in is
impossible (`login` also answers 503). The panel has thrown away a session that the server would still accept for the
one operation that matters.

Scenario: the administrator stops the system-database instance (the dialog promises the panel will show a Start
button), then reloads, opens a bookmark, or the browser restores the tab.

Confirmed: yes. Test against the mock: sign in, build a new app instance (a reload) while the stopped flag is set:
final route `/login?redirect=/dashboard`, `isSignedIn` false.

Fix: in `restore()`, when the failure is `system_database_stopped`, keep the state "unknown session", render the
stopped page with the Start button (it only needs the cookie and the CSRF token, but the token comes from
`getSession`; so also keep the CSRF token of the previous page load in `sessionStorage` for this case, or tell the
administrator plainly that after a reload the instance must be started on the machine). Whichever is chosen, the login
page's 503 message must say what to do.

### W2-03 medium - "Matched the fingerprint you gave" is a client-side claim

Where: `src/pages/SetupPage.vue:563-568` (the `join-fingerprint-note`).

What happens: after a join task is `done`, the page prints either "The certificate of the existing server matched the
fingerprint you gave." or the trust-on-first-use text, chosen by `join.expectedFingerprint.trim()` (what the user typed),
not by anything in the task or node state. By contrast `FingerprintValue` in the add-server dialog and server pages
uses `fingerprintPinned` from the server, which is the right source. The wizard has no server field to use (the node
is not signed in), but it can read the setup task detail.

Scenario: the administrator types a fingerprint, the server (an older 0.3.0 build that reads only the
`X-Kingres-Pin-Sha256` header, or any build that ignores the unknown member) does not pin; the join succeeds and the
page says the certificate matched.

Confirmed: by reading only (the text depends on `join.expectedFingerprint` only). I did not check the wizard tests for a
server that did not pin.

Fix: show "matched" only when the task detail or the node state says the pin was checked; otherwise say "you gave a
fingerprint; the server did not report that it checked it". Combined with W2-04, also send the normalized value.

### W2-04 medium - The fingerprint is validated leniently and sent raw

Where: `src/lib/fingerprint.ts:8-21` (`normalizeFingerprint`, `fingerprintError`); the bodies are built in
`src/pages/SetupPage.vue:140-142` and `src/components/ServerActions.vue:66-68` with `.trim()` only.

What happens: the validator strips colons and any `\s` (including tab and U+00A0) before testing for 64 hex digits, but
the request carries the value as typed. The contract says "hex, colons allowed" (`openapi.yaml:3827`, `:4656`), not
white space. The panel itself prints fingerprints in groups of eight separated by spaces (`groupFingerprint`,
used by `FingerprintValue`), so a person who copies the displayed value, or one from `openssl` with colons and
upper case, passes validation and sends text the server may refuse (fail-safe, but it teaches people to leave the
field empty) or, on a server that normalizes differently, may compare differently.

Confirmed: yes, with a script over the real module: the grouped value, a value with U+00A0 in the middle, and the
upper-case colon form are all accepted by `fingerprintError`; the sent value for the grouped one is the grouped string
with spaces. The validator rejects `sha256:` and `0x` prefixes and the `openssl` "SHA256 Fingerprint=" line, which is a
reasonable strictness but unexplained. Related mock defect: `src/mocks/handlers.ts:262` strips `/[:s]/` (a colon or
the letter "s", not white space), so the mock refuses a spaced pin as a mismatch. That hides nothing today but shows
that this path is tested only with canonical input.

Fix: send `normalizeFingerprint(value)` (64 lower-case hex digits, no separators) from both call sites; make the mock
use `\s`; add a test that the request body contains exactly 64 hex digits for grouped, upper-case and colon input.

### W2-05 low - The shown verification command has a literal `\n`

Where: `src/components/ledger/ProofResult.vue:21`: the template literal contains `\\n  --row-hash`.

What happens: the `<pre data-testid="verify-command">` shows `... --table-id 5 \n  --row-hash <hash ...>`: a backslash
followed by the letter n. Copied into a shell, `\n` becomes an argument `n` and the command fails or means something
else. The test `tests/ledger-0-4.test.ts:87-92` checks substrings only, so it passes.

Confirmed: by reading (the escape is unambiguous in the source). Fix: use `\\\n` (backslash and a real newline) or a single
line; assert the exact text in the test.

### W2-06 low - Proof values come from the float copy; the view is an unchecked cast

Where: `src/lib/ledger-proof.ts:42` (`JSON.parse(raw) as ProofView`), `src/components/ledger/ProofResult.vue:39-50`.

What happens: only `table_id` is read from the raw text. `seq`, `ledger_txid`, `shard_group_id`, `entry_index`,
`entry_count`, `tx_index` and the block fields are shown from the parsed numbers, so an integer above 2^53 (a 64-bit
sequence or an `xid8`-derived id is plausible) is shown rounded while the saved file is exact; the user compares the
screen with the file and sees two numbers. The cast also means a proof without `block`, `entry_path`, `tx_path` or `chain`
throws in the render (`v.block.tx_count`, `v.entry_path.length`), and the page shows nothing instead of "unexpected
answer, here is the raw text".

Confirmed: by reading only (the saved bytes are unaffected: see W2-07 for that).

Fix: read every displayed integer with `rawSlices` as `table_id` is, or display `BigInt` from the raw slice; check the
shape of the parsed value (required members, arrays) and fall back to "show raw text and the download button".

### W2-07 low - `raw-json.ts`: hang on invalid input, duplicate keys, silent fallback

Where: `src/lib/raw-json.ts:23-27` (string scanner), `src/lib/ledger-proof.ts:57-70` (`withRawDocuments`).

I attacked the extractor with: braces and escaped quotes inside strings, `\\` before a closing quote, `}`,
nested arrays and objects, 23-digit and `1E+400` numbers, `-0.0e-0`, astral characters, extra white space around
colon and comma, the target as a later member, a same-named key nested elsewhere, an escaped key (`"a"`), empty
containers and literals. Every valid-JSON case returned exactly the original characters. That part is sound.

What is not:

1. On text that `JSON.parse` would refuse (a string never closed, truncated input) the scanner loops forever:
   `while (text[i] !== '"') i += ...` has no bound. Today both callers call `JSON.parse` on the same text first
   (`ledger-proof.ts:41`, `endpoints.ts` digest functions), so the state is unreachable; a later caller that skips that
   step would hang the tab. Confirmed (the process had to be killed by timeout on `{"a":"abc`).
2. With duplicate members `{"document":{"x":1},"document":{"x":2}}` the scanner returns both slices; `slices.find`
   takes the first while `JSON.parse` (and most verifiers) take the last. The bytes saved are the server's, but the
   file the user saves and the document the screen shows can differ. Confirmed with the scanner (two slices returned).
3. `rawDocument = hit?.raw ?? JSON.stringify(chain.document)` (`ledger-proof.ts:70`) silently saves a re-serialized
   document if no slice is found: not byte-exact, big integers lost, and `undefined` if `document` is absent. I found no
   input that reaches it for a conforming response, so this is a latent path, but it is exactly the failure the module
   exists to prevent, and it is silent.

Fix: bound the loops (`i < text.length`, throw `SyntaxError`); throw instead of falling back, and show "this digest
cannot be saved exactly"; reject a response with duplicate `document` or `chains` keys.

### W2-08 low - Invisible whitespace in names

Where: `src/lib/safe-text.ts:73` (`if (char === ' ') return false`), `analyseName` (`:297`, first 300 characters only).

What happens: an ordinary space is never drawn as an escape and never counted, so `orders`, `orders ` (trailing space)
and ` orders` look identical in tables, selects and confirmations, and a double space inside a name is
indistinguishable from one. A user who may create tables or databases can create a name that imitates another with
one extra space. `TypeToConfirm` does not show its "hidden characters" hint for such a name (`hasHidden` is false), so
the administrator cannot tell why typing the visible name does not enable the button. Separately, a hidden character
after position 300 is escaped when the value is shown in full, but gets no warning badge (`analyseName` stops at 300).

Confirmed: with the real module, `nameWarnings` for `"orders "`, `" orders"` and `"or ders"` is empty and `hasHidden`
is false; for `"x"*300 + U+202E`, `nameWarnings` is empty and `hasHidden` true.

Fix: flag (`kind="name"`) leading, trailing and consecutive spaces ("contains leading/trailing space") and show them
with a visible marker in `TypeToConfirm`; scan the whole name (it is bounded by the 63-byte identifier limit for real
identifiers anyway; only messages are long).

### W2-09 low - Text that bypasses `SafeName`

The first review asked for one component everywhere; this is the list of places I found that still print server-supplied
text raw (Vue escapes it, so there is no injection; the issue is spoofing and invisible characters):

- `src/layouts/ShellLayout.vue:76-78`: the cluster name in the top bar and `title` (cluster id). A cluster name is
  administrator-chosen, but for a joined cluster it comes from a peer.
- `src/pages/ForbiddenPage.vue:18`: `session.username`.
- `src/components/ServerActions.vue:174`, `:207`, `:214` and `src/pages/DashboardPage.vue:125`: server and leader
  addresses inside the sentences of the remove and failover confirmations (the typed-confirmation field itself is
  safe).
- `src/pages/LedgerPage.vue:481-482`: anchor `target` and `status` in the digests table.
- `src/components/CreateDatabaseDialog.vue:184`, `:191`: encoding and collation names (catalog values).
- `src/components/security/RoleDialog.vue:207`: cluster-role name and description.
- `src/pages/ThisServerPage.vue:76-80`: `nodeState`, `version`, `serverId`; `src/pages/RebalancePage.vue:186` `phase`.

Impact is small for each; the point is the list is not empty. A lint rule or a `<RawText>` wrapper that fails the
build on a bare interpolation of a string-typed schema property would keep it that way. Confirmed by search over the
templates.

### W2-10 low - Leave cluster offers force on any 503

Where: `src/components/this-server/LeaveClusterDialog.vue:42-44` and `:74`; `src/api/problem.ts:28-42`
(`networkError` makes code `service_unavailable`); `src/api/client.ts` (`codeForStatus` maps 502, 503, 504 to the same
code).

What happens: the dialog treats `service_unavailable` as "the manager leader cannot be reached" and then offers the
"Leave anyway (force)" box with the sentence that the cluster is not told and the certificate is not revoked. That
code is also what the client invents for a request that never reached the server (browser offline, aborted) and for a
proxy's 503 page. The contract (`openapi.yaml:698-700`) gives 503 `service_unavailable` for the leader case, so the
code alone is ambiguous. The consequence text is accurate, the cause text can be false, and force is still gated by
the typed server name and a checkbox, so this is low.

Fix: offer force only for a response that is a problem document from this server (not synthesized by the client) and
say "this server could not reach the manager leader, or the answer was lost"; after a network failure, ask the user to
check whether the server is still a member first.

### W2-11 low - Unknown status values break the page

Where: `src/lib/status.ts` maps (`SERVER_STATUS`, `TASK_STATE`, `LEDGER_STATE`, `HEALTH`, ...) indexed without a
fallback, used as `:meta="SERVER_STATUS[s.status]"` (`ServersPage.vue:79`, `ServerDetailPage.vue:111`, ...);
`src/components/StatusBadge.vue:11-12` reads `meta.tone`.

What happens: a value the panel does not know makes `meta` undefined and the template throws. The contract promises
open enums only for `TaskKind`, `AlertKind`, `AuditAction` and `ProblemCode` (`api/README.md:321`), and the panel
handles those (`taskKindLabel`, `alertKindLabel`, `unknownEntry`). The status enums are not promised open, so this is
low, but 0.5.0 already added members to enums and the failure is a half-rendered page.

Confirmed: yes. Mock with one server status set to `quarantined`: `/servers` rendered 2 of 3 rows and Vue logged
`TypeError: Cannot read properties of undefined (reading 'tone')` and `Cannot destructure property 'type' of 'vnode'`.

Fix: a `statusMeta(map, value)` helper returning a neutral "unknown (value)" badge through `SafeName`; or an
`app.config.errorHandler` plus an error boundary per page.

### W2-12 low - The setup token outlives the wizard

Where: `src/api/client.ts:22`, `:29`, `:37` (module variable, header added to every request); `src/pages/SetupPage.vue:202`,
`:207`, `:234`.

What happens: the token is cleared when it is rejected and in `finish()`. There is no cleanup when the page unmounts
for another reason (the user navigates away after a failed task, the node becomes initialized from another tab and the
guard redirects to sign-in, the browser back button). The token then stays in memory and `X-Setup-Token` is sent on
every later request to the same origin, including after the administrator signs in, until the page is reloaded. The
token is one-time and same-origin, and nothing persists it (no storage, no URL), so the harm is limited. The same
component also keeps the administrator password in its reactive state until unmount (normal), and keeps it filled in
after a failed task (`backToForm`).

Confirmed: by reading only. Fix: `onBeforeUnmount(() => setSetupToken(null))`; clear `adminPassword` fields when the
task fails to start.

### W2-13 low - Consequence wording against the contract

- Drop database (`src/pages/DatabaseDetailPage.vue:281-290`): "All tables and data ... are deleted on every server,
  including the replicas." matches `dropDatabase` ("Drops the database on every shard group. Irreversible"). It does not
  say that for a ledger database the hash chains, blocks and the ability to verify earlier digests of that database
  are deleted with it ("Ledger tables do not protect a database from being dropped; the audit log keeps the record").
  For the one database type whose purpose is tamper evidence this should be said, with the digest-download hint.
- Remove server (`src/components/ServerActions.vue:173-176`): says "unregistered, reset to an unconfigured server, and
  its certificate is revoked". The contract also says the server is told to "delete its instance" and the task runs as
  `decommissioning`. The panel's sentence about data is about buckets only; the local PostgreSQL instance and its data
  on that machine are deleted.
- Stop of the system-database instance (`InstanceActionDialog.vue:69-73`) is described well, but Restart of the same
  instance (`:49` only types for `stop`) is not: a restart pauses the same operations for the restart time.

Confirmed by reading the text against `openapi.yaml:951-953`, `:1324-1327`.

### W2-14 low - Database named `..` or `.` (W-15, route side)

Where: `src/pages/DatabasesPage.vue:70` (`router-link` to `{ name: 'database', params: { name: d.name } }`); the API guard is
`src/lib/path-segment.ts` and `src/api/client.ts:64-77`.

What happens: the API client refuses `.`, `..` and empty names with an explanatory error (closed, see below). The route
does not: the link to a database named `..` becomes `/databases/..`, which the browser resolves to `/`, so a click goes
to the dashboard with no message. The database cannot be opened, dropped or inspected from the panel. Confirmed by
the URL rules for `pushState` (reasoned; not run in a browser). Fix: do not render a link for such names; show the same
"This name cannot be used in a request" text.

### W2-15 low - Digests list has no paging

Where: `src/pages/LedgerPage.vue:78` (`listLedgerDigests(..., { limit: 10 })`, `moreNotShown` only drives a notice).

What happens: the Digests table is the only way in the panel to obtain a digest document for `kingres-verify`. Only the
newest ten are listed; the notice says more exist but offers no "load more". A proof for an old block that needs an older
digest cannot be completed from the panel. Fix: reuse `usePagedQuery` as for blocks and verifications.

### W2-16 note - Coverage and scope

- `browser-tests/harness.ts:203-221` lists 17 routes; none of the browser tests (axe, CSP, layout) opens the ledger proof
  result, the leave-cluster dialog, the instance action dialog, the system-database-stopped state, the add-server dialog
  with the fingerprint fields, or the wizard's join form. These are the 0.4.0 additions. Their jsdom tests exist and pass
  (axe via `vitest-axe` in `tests/pages-a11y.test.ts` covers pages, not these dialogs). A blob download under the CSP
  (`a[download]` with an object URL) is not exercised either; I expect it to work (no CSP directive governs it) but did
  not see it run.
- Contract operations without a UI: `renewServerCertificates` and `revokeServerCertificates` (admin) have no
  button; the panel shows certificate expiry and a "Revoked" badge but the action needs the API. Not a defect if the
  README says so; I did not find that it does.

## Examined and found sound

- Injection sinks: no `v-html`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval`, `new Function`, `window.open` or
  `postMessage` in `src/`; no `:href` or `:src` built from data; `:style` only with numeric percentages (task progress,
  meters, rebalance) and token colours; the only dynamic component is the development-only demo hint. Clipboard: one
  write, of the expected name in `TypeToConfirm`. Downloads: file names are fixed text or numeric ids
  (`proof.json`, `digest-<id>-group-<n>.json`), contents are the exact response text, no BOM, no added newline.
- Open redirect: `safeRedirect` run against `//host`, `/\host`, `/%5Chost`, `/%2F%2Fhost`, tab and NUL, `https:`,
  `javascript:`, `///` all return `/`; inputs such as `/.//host` are kept but are paths that `router.push` and
  `pushState` keep on this origin. A different user signing in after an expiry is sent to `/` (`LoginPage.vue:36-39`).
- Session and storage: the CSRF token and the setup token are module variables; `localStorage` holds only the theme,
  nothing else is persisted (search), no credential is placed in a URL or log. The workbench keeps no history. After
  sign-out, expiry, another user in the session or another tab, every server-derived structure is reset in one place
  (`server-state.ts`); late answers are aborted (`client.ts` `inFlight`) or ignored (task poller generations).
- Authorization as shown: `GateButton`, the navigation and the route guard take the role from the generated
  `x-required-role` map (`operations.generated.ts`); the guard redirects a deep link to the forbidden page; I found no
  destructive action offered under a harmless label. Note that the grants matrix uses `createGrant` for the revoke
  too; both are `kingres_admin` in the contract.
- Task polling: stops on settle, on `reset`, on scope disposal and on sign-out; does not poll in hidden tabs or while
  the server is paused on purpose; a 401 in a poll goes through the same session-loss path.
- Degraded states: the paused client (offline manager) avoids request storms in the stopped state; the stopped page
  watches with one cheap call every five seconds (`recovery.watchMs`); `shouldRetry` does not retry
  `system_database_stopped`.
- Fingerprint display: `FingerprintValue` shows "pinned" only from the server's `fingerprintPinned`, and shows the
  not-pinned text with the consequence when it is false or the fingerprint is null.
- Ledger evidence: the panel never says "verified" on its own authority; `ProofResult` states that the check is done by
  `kingres-verify`, not by the panel or the server; verification state badges come from the server's field.
  `raw-json.ts` returns exact slices for every valid input I tried (W2-07 lists the invalid-input and duplicate-key
  cases).
- Build and supply chain: `dist/` has no source maps, no mock or MSW code, no service worker (it is served by a
  development-only plugin), no demo strings; only five runtime dependencies; CSP: no inline script, `eval` or `data:`
  URL in the bundle, and the browser CSP test passes with the README policy. `npm ci` prints a notice that `vue-demi`
  has a postinstall script not covered by an `allowScripts` policy; `DEPENDENCIES.md` documents it.
- Dialog behaviour in code: focus trap, Escape (blocked while a request starts), focus return, background `inert`,
  labelled by the title; double submission on typed confirmations is prevented by `isStarting` and by disabling the
  button.
- Checks passing: typecheck, lint with prettier, 396 unit tests, 17 browser tests (axe on 17 routes in two themes and two
  widths with hostile data, a dialog case, CSP, layout).
