# Security note: the schema of an extension is not trusted by its name (2026-11-23)

Status: fixed in the first part (the helper, the readers listed below, the extension scripts); the other call sites of the control plane are fixed on top of the
same helper by a second change.

## The issue

The service role `kingresd` is the bootstrap superuser and opens sessions in user databases. Three things were wrong.

1. **The presence of an extension was decided by a name.** The control plane tested `to_regclass('kingres.X')` or `to_regprocedure('kingres.f(..)')`, or a row
   of `pg_extension` by name, and then read or called `kingres.*` in the superuser session. Nothing checked that the object belonged to the extension. A role that
   owns a database, or has CREATE on it, can make a schema `kingres` with a view of the name that is tested, and a function of its own that the view calls: the
   function then runs as a superuser. The monitor loop visits every database on a timer, so no click was needed.
2. **The pgstore connections and a few others did not fix `search_path`.** A database owner can set `search_path` for the database, and an unqualified name in a
   statement of the control plane (a function, an aggregate, a catalog relation) then resolves to an object of the owner. The ops paths already used
   `safeServiceSession`; the store, the authenticator and the engine pool had been missed.
3. **The extension scripts reused a schema that already existed.** `kingres_shard` (`CREATE SCHEMA` only when absent) and the extensions with `schema = ...` in
   the control file (`kingres_ledger`, `kingres_timepart`, `kingres_columnar`, `kingres_sketch`) used a schema that a role had made in advance. The extension then
   lived in a schema owned by that role, which could add overloads that the SECURITY DEFINER functions resolve, or drop and recreate the objects.

## The fix

* **`internal/extguard`** decides, with one catalog query, whether an extension can be trusted: the extension has a row in `pg_extension` and a superuser owns it;
  a superuser owns its schema; the ACL of the schema grants CREATE to no role that is not a superuser (PUBLIC included); and every relation, function, type,
  operator and other object in the schema is a member of an extension owned by a superuser (`pg_depend`, deptype `e`; the extensions that share the schema
  `kingres` count for each other). The answer is installed, absent (not an error) or untrusted (a typed error). `Guard` caches the answers for one transaction or
  one pass of a loop. `PreInstall` runs the same checks on the schema that an extension is about to be created in. `StatusSQL` gives the check as a statement
  without parameters, for the places that can only send text to another server.
* **The readers check before they read.** pgstore (every relation of the schema `kingres` goes through one function that verifies the extension that defines it;
  the probes of the database list, the cluster settings, the columnar and time partitioning readers), the monitor (the ledger queue; one pass verifies every
  extension of every database), ledgerround (the reads of a group and the list of groups), the ledger operations (digests, verifications, proofs, client keys),
  the extension operations (installed version, install, update, self test), grants (ledger tables, the sharding test), the approximate-aggregate status of the
  other servers, and the apply of the databases of the cluster (`kingres_shard` and the extensions created from the list).
* **An untrusted extension is refused, never read.** The operations answer with a conflict that names the check; the readers of the store treat the feature as not
  available; the monitor raises the alert `extensionSchemaUntrusted` (critical, one per database, subject `server:<id>|database:<name>`; contract 0.24.0,
  a placeholder revision) and clears it when the schema is trusted again.
* **Before CREATE EXTENSION and ALTER EXTENSION UPDATE** the control plane refuses a target schema that exists with an owner that is not a superuser, that grants
  CREATE to such a role, or that holds an object that does not belong to an extension.
* **`cluster.SafeSession`** (and `cluster.NewSafePool`) fix `search_path = pg_catalog` in the startup parameters, which outrank the settings of a database and of a
  role. pgstore (`New`, `SetDSN`, so the pools and the connections to other instances), the authenticator and the pools of the task engine use it.
* **The extension scripts** raise an error when the schema exists and is owned by a role that is not a superuser, or grants CREATE to such a role or to PUBLIC:
  kingres_shard 0.9 (generated by `mk-install-script.sh`), kingres_ledger 0.3, kingres_timepart 0.2, kingres_columnar 0.2 and kingres_sketch 1.0. These versions
  are not released, so their scripts were changed in place; the upgrade scripts are untouched (an existing installation is protected by the run-time check).

## Tests

Unit tests of the classification and of the statement; PostgreSQL tests of every failing case (a schema owned by a tenant, a view and a function that are not
members, CREATE for PUBLIC and for a role, an extension owned by a role that is not a superuser); mutants of each check in the statement and of the pre-install
statement; `TestSchemaSpoofIsNeverExecuted`, which plants views, functions and a shadowing `search_path` that write a marker and runs the monitor, the store, the
ledger reads and the extension operations against them; one TAP test per extension that pre-creates the schema as a tenant.

## What remains

The call sites that the second change covers (table, partition and storage operations, schemas, server groups, databases, transfers, rebalance, membership,
failover, standby and the rest of `cmd/kingresd`) use the same helper. Until then they still carry the old tests. An installation that was made before this
change keeps a schema that a tenant may own; the alert `extensionSchemaUntrusted` shows it, and the operator must restore the owner and the grants.

## Additions

* **kingres_shard and pg_catalog.** kingres_shard is created with `SCHEMA pg_catalog` and its script makes the schema `kingres`. extguard therefore checks
  the schema `kingres` for it (owner, ACL, foreign objects) and never looks for foreign objects in pg_catalog. The members of kingres_ledger,
  kingres_timepart and kingres_columnar in `kingres` are not foreign.
* **The system database `kingres_system`.** The readers of `kingres.*` and `kingres_cp.*` in it do not check an extension, because the service role owns the
  database and no tenant is meant to have CREATE there. Defence in depth: at cluster init and at every start (`MigrateSystem`) `HardenSystemDatabase` revokes
  everything of PUBLIC on the database (CONNECT, TEMPORARY) and CREATE in its schema `public`, and grants CONNECT to the cluster roles only (kingres_admin,
  kingres_ops, kingres_readonly, kingres_stats): a console sign-in connects as the signing-in role, which is a member of one of them. A role with the right
  password and no cluster role is answered like a wrong password (SQLSTATE 42501 is mapped to invalid credentials). The monitor checks the database in
  every ledger pass (`extguard.SystemDatabaseProblems`: a superuser owns the database and its schemas kingres, kingres_cp and public, and no role that is not a
  superuser can create schemas or objects there) and raises `extensionSchemaUntrusted` for `database:kingres_system` when it does not hold.
* **A finding in the C library (not fixed here).** The library of kingres_shard takes the catalog to be present when relations named node, colocation,
  dist_table, bucket_map, map_version and local_node exist in the schema `kingres` of any database, without asking whether they belong to the extension, and then
  scans them. Views of a tenant with those names made the backend fail with a segmentation fault (observed on PostgreSQL 18); tables of a tenant would be taken
  for the routing catalog. The fix is a separate change (branch xcat-fix); the spoof test leaves two of the six names out so that it does not crash the server.

## Run-time objects of kingres_shard (check 4)

A bucket move, a split, a drain and the rebuild of a table make objects in the schema `kingres` that are not members of the extension. They are made by the
extension's own C code and SQL functions, as the service role, and they keep the owner of the table they come from. The first form of check 4 refused a database
while one of these operations ran. What the extension makes there, by reading `bucket_move.c` and `kingres_shard--0.9.sql`:

* the orphan of a moved bucket (`orphan_<move>_<bucket>`), its partitions (`..._l<n>`) and the orphan of a split (`orphan_s<split>_<ordinal>`): tables, renamed
  and moved by `ALTER TABLE ... SET SCHEMA kingres`, owner unchanged (the owner of the distributed table);
* the old copy of a rebuilt table (`kingres_old_<oid>...`) and its identity sequences (`kingres_old_<oid>_s<attnum>`): the same;
* the log of a table operation (`tlog_<op>_1`) and its identity sequence: made by the service role;
* the trigger function of a split (`split_capture_<split>_<ordinal>`): SECURITY DEFINER, `RETURNS trigger`, given to the owner of the table;
* indexes, TOAST tables and the row types of these tables, which check 4 never looks at on their own.

The rule is the narrowest one that lets these through:

1. The object must be a table or a sequence of one of the name patterns above (a sequence only when it belongs to such a table), or a function of the name
   `split_capture_<n>_<n>` that returns trigger. A view, a type, an operator or any other function that is not a member is always foreign, whatever its name.
   A table named like a table that the control plane or the C library reads (node, colocation, dist_table, bucket_map, map_version, local_node, the ledger
   tables, the timepart policy and so on) matches no pattern and is foreign; the patterns share no prefix with those names.
2. The owner does not matter. A role that is not a superuser cannot create or rename anything in `kingres` (checks 2 and 3), so the owner adds no
   information, and an owner test would turn ordinary flows into an untrusted database: the tenant drops or undistributes its last distributed table before
   the cleanup of a move, the orphan stays under its owner, and a database that disappears from the listings makes a drain count zero buckets. A database that
   cannot be verified is an error or "not readable" for the listings and the drain, never an empty one.
3. The trigger function of a split must be what the extension makes: SECURITY DEFINER, language plpgsql, `proconfig` exactly `search_path=pg_catalog, pg_temp`.
   The owner of the table owns the function and can ALTER it (SECURITY INVOKER, another search_path) without any CREATE privilege; any such change makes it
   foreign.
4. Only the schema `kingres` counts for the run-time objects, whichever schema the extension is in. For kingres_shard the schema `kingres` is always checked
   (owner, ACL, foreign objects) as well as the schema in `pg_extension.extnamespace`, which is pg_catalog when the extension is created as the install script
   expects; pg_catalog itself is never searched for foreign objects.

Why check 4 still matters when checks 2 and 3 stop non-superusers from creating objects in `kingres`: a schema that a superuser made before the extension
existed (an operator's mistake, or a restore), objects that `ALTER ... SET SCHEMA` moved in before the grants were fixed, a dump that restored objects into the
schema, and objects made while an earlier version of the extension was installed. None of them is a member, and the service role reads names in that schema.
The run-time rule only widens check 4 for what the extension itself makes, by name, kind and owner.

Tests: a real install with a distributed table and an orphan (also after the last distributed table is dropped, and for an orphan of any owner), a split table, an old copy, a log with its identity sequence and a trigger function (superuser
and table owner) verifies as trusted; a non-member function or view with a run-time looking name, a function of the right name with another type, a table named like a
catalog table, a sequence of no table and run-time objects of a role that owns no distributed table are refused; six mutants of the rule are killed.
