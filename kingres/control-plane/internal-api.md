# The internal API of kingresd

Status: version 1 (internal protocol version, independent of the public contract
revision). Design: `kingres/docs/design/control-plane-3.md`, decisions D1 and D2.
Implementation: `internal/internalapi`, `internal/pki`.

The internal API is how the servers of one cluster talk to each other. It is
**not** part of the public REST contract and may change with every binary
version; a server refuses a peer that speaks another version.

## Transport and authentication

- A separate TLS listener (setting `internal-listen`, for example `0.0.0.0:8092`).
  The public listener never accepts a client certificate as authentication and this
  listener never accepts a session, a bearer token or a setup token.
- TLS 1.3 only. The server presents the server certificate of its cluster
  (`<data-dir>/pki/server.crt`); the client must present a certificate too
  (mutual TLS).
- A client certificate is accepted only if it is signed by the cluster CA, is
  within its validity, is usable as a client certificate and its serial number is
  not on the revocation list. The common name of the certificate is the caller's
  server id. The check is made at every request, not only at the handshake: a
  connection that was opened with a certificate that has expired since is refused
  (`certificate_refused`), which is why a server closes its idle connections to the
  others when it has installed a renewed certificate.
- Every certificate is an ECDSA P-256 certificate whose key was generated by the
  server that uses it; the CA only ever sees certificate requests. A renewed
  certificate is made for the key the server already holds (see "Certificate
  renewal").
- A server that calls a server whose certificate is revoked refuses to connect (the
  revocation list is checked against the peer's certificate too), except for the
  two calls that must still reach a cut-off server: the revocation list
  (`POST /pki/install`) and `POST /node/reset`.

## Versioning

Every request carries `X-Kingres-Internal-Version: <n>`. The server answers `409`
with `{"error":"version_mismatch","message":"This server speaks internal API
version 1, the caller \"2\"."}` when the number is missing or different.

"Member" means a server that the leader's catalog records as `active` (or `removing`, which must still be able to ask how its removal went). A server that holds a certificate of the cluster but has not been admitted yet (`pending`: the certificate was issued and installed, the add task has not finished) is **not** a member: it may make only the calls of its own join, which the leader makes on it, and every call marked "member" is refused with `403 not_member`. Every certificate the cluster signs for a server that is not yet a member is therefore a certificate that authorizes nothing but that join.

"Leader" means the caller's certificate names the server that holds the primary of
shard group 0, read from the catalog; while that is unknown no leader-only call is
accepted. A path or method that is not in the table is `404`.

The API never executes a path, a program name or SQL taken from a request, with
one exception: `POST /internal/v1/exec`, which is restricted to the leader. Its
body is `{"database": "...", "sql": "...", "rowLimit": 1000}` (SQL at most 1,000,000
bytes, row limit at most 10,000); the server logs the caller, the database, the
length and a hash prefix of the statement, never its text.

**The leader of a server that is held back.** A server whose instance waits for its group lease (the old primary of a failover, stopped and kept from
starting until it is a standby) cannot read its catalog and does not know the leader: its leader-only calls answer `503 service_unavailable`, and a
task step waits for it. Three calls (`POST /standby/plan`, `POST /standby/rebuild`, `GET /standby/status`) have the policy "leader or held back": while
the server is held back it asks the other servers of its peer directory `GET /leader` (any peer answers; the answers count when every server that
answered names the same leader; kept three seconds) and accepts the call of the server they name. Without an answer it stays `503`. The rebuild of an
old primary proves what it needs itself (internal-api.md, "Standbys"), so this widens nothing a member could not already do to its own instance.

## Forwarding an operation to the leader

`POST /internal/v1/forward` is how a server that is not the manager leader hands a cluster operation to
the leader (design D6). Any server of the cluster may call it; a server that is not the leader answers `409
not_leader` whoever asks. The body is

```
{"operationId": "createRole", "pathParams": {"roleName": "x"}, "query": "", "contentType": "application/json",
 "body": "<base64 of the request body>", "identity": {"username": "alice", "clusterRoles": ["kingres_admin"]},
 "requestId": "...", "sourceAddress": "203.0.113.5", "source": "panel"}
```

and the answer `{"status": 201, "header": {"Content-Type": "..."}, "body": "<base64>"}`, which the
forwarding server relays unchanged (only Content-Type, Location, Retry-After, Allow and Content-Language are
passed on).

What the leader does with it: it looks the operation up by id (a path is never accepted), refuses an operation
that is not leader-bound (sign-in and sign-out, setup, the operations on this very server, the query workbench,
the acknowledgement of an alert (it goes to the server that holds the alert), and reads other than listTasks, getTask, getClusterSettings, listServerGroups, listServers (a follower asks for it to take the groups, fingerprints and certificate expiry of the servers from the leader's system database; the public listServers is answered locally), listLedgerVerifications and getLedgerVerification; createInclusionProof is not forwarded either), requires the path parameters to be
exactly the operation's, rebuilds the URL from the contract's template with escaped values, checks the identity
(user name, only the four cluster roles), and runs the request through the same pipeline as a public one: query
validation, the role the operation requires (so a server cannot raise an identity's privileges beyond what it
claims; the leader also derives the claimed role's cluster roles itself, from its own catalog, and refuses an identity that is dropped, cannot log in, is expired or does not hold the claimed roles (CP-07), and refuses a forwarding server that is not a member of the cluster and an identity whose proof it cannot verify; see the next section for what a compromised member can still do), the handler and the audit.
The identity is **not** taken on the word of the forwarding server, see the next section. The audit event is written by the leader, once, with the details `forwardedBy` (the server id in the caller's
certificate) and `originRequestId` (a handler that sets details of its own does not drop them); the forwarding
server writes none, unless the leader could not be reached (then it answers 503 and audits the failure itself).
The leader makes the role connectable for its own connections (the same step as a sign-in) only after the
identity was proven and the role check passed, because the forwarding server verified the password.

### Forwarded identities need a proof

A certificate of the cluster says "this is a server of the cluster". Before 0.6.0 that was enough to act as any
existing role by name (second review, CP2-01; first review, CP-07): the leader derived the role's cluster roles
from its own catalog, but nothing showed that anybody had signed in as that role. Now a forwarded request carries
a proof that the sending server holds a session of the user it names, and the leader checks it against the user's
verifier in its own PostgreSQL (`pg_authid.rolpassword`) before it does anything else:

- At sign-in the server that verified the password derives the SCRAM ClientKey of the password under the salt
  and iteration count of the role's stored verifier and keeps it in the in-memory session (never on disk, never
  sent). A role without a SCRAM-SHA-256 verifier gets a session that works on this server but cannot be forwarded.
- With every forwarded request the server sends `proof = {issuedAt, nonce, value}`, where
  `value = ClientKey XOR HMAC(StoredKey, digest(request) || issuedAt || nonce)` (the proof of RFC 5802 with the
  request in place of the SCRAM authentication message). `digest` covers the call kind, the sending and the
  receiving server, the user name, the claimed cluster roles, the operation id, path parameters, query, content
  type, SHA-256 of the body, request id, source, source address, pin and ordinal.
- The receiver reads `StoredKey` from the verifier, recovers `ClientKey' = value XOR HMAC(...)` and accepts when
  `SHA-256(ClientKey')` equals `StoredKey`. **The receiver therefore learns the user's ClientKey**, exactly as a
  SCRAM server does, and the ClientKey is password-equivalent (it makes proofs for that user toward any server
  and authenticates to PostgreSQL by SCRAM). That is why a proof is sent to the manager leader only: the leader
  holds every verifier, runs every cluster operation and is trusted with everything already. **A compromised
  leader is a compromised cluster; that is inherent** (it is also the server that holds the CA key in the
  current design).
  **One exception (F4-05, ADR 0026):** the request of an operator for the failover of the map group is sent with a proof of kind `mapStart` to the candidate that
  promotes the map group, because the leader is the server that is gone. The candidate is the next leader and already holds every verifier, and may learn the
  operator's ClientKey; it ends when the password changes. A session of the token kind has no proof key and gets `503 service_unavailable` for this operation when the
  candidate is another server.
- It refuses a proof whose `issuedAt` is more than two minutes from its clock and a nonce it has accepted before
  (a bounded replay cache that only fills with proofs that verified). The answer to a refused proof is
  `401 identity_unproven`; the forwarding server tells its client `401 unauthenticated` ("sign in again").
- A proof is made for one request, one sender and one receiver: it cannot be used for another operation, body,
  query, user, role set or pin, replayed or sent on to another server. A changed password changes the verifier
  and ends forwarding for every older session at once.
- The leader still derives the roles itself and refuses an identity that is dropped, cannot log in, is expired or
  does not hold the claimed roles; the audit event names the forwarding server (`forwardedBy`).

A proof is sent to the server the sender believes to be the leader, and an internal call is refused before its body
is read when the receiver is not the leader; the only way a non-leader receives a proof is a sender whose own view
of the leader is wrong (a leader change in progress), and the sender checks the receiver's certificate against the
name it dials.

### Gather: the leader's assertion

`POST /gather` goes to **every** member, so it must not carry a proof: a single compromised member would learn the
ClientKey of every user whose cluster-wide read it answers and could forward as that user. The asking server
therefore sends the gather request with the proof of the user's session to the leader only
(`POST /gather-authorize`, member-only like `forward`, kind `gather-authorize`). The leader checks the proof as for
a forward and answers with an **assertion** signed with the key of its own server certificate:
`{leader: <certificate DER>, issuedAt, nonce, signature}`, over a digest of the asking server, the user, the claimed
roles, the operation, path parameters, query, content type, body hash, request id, source and source address (not
the receiver and not the ordinal: one assertion serves every server of one request). When the asking server is the
leader it signs the assertion itself; the session was opened on it.

A member accepts a gather call only with a valid assertion: the leader's certificate is accepted by the cluster
(chain, usage, validity, revocation list), its server id is the leader **this member** knows, the signature
verifies, `issuedAt` is within two minutes, the nonce was not used, and the digest matches a request whose asking
server is the caller named by the mTLS certificate. Therefore a member that received an assertion cannot use it
(it is not the asking server, the request is fixed and it is used once), a member's own key signs nothing the
others accept, and a gather request that carries a proof is refused with `400`. The member still derives the roles
again from its own catalog before it answers (the check of CP-07), so the assertion only proves "the leader saw a
session of this user at this server"; it never widens what the user may do. When the leader cannot be reached or
cannot check the proof (its instance is stopped), the gather call is refused and the server shows up as missing
(`refused`) in the answer.

What a compromised **non-leader member** can do: it holds its own PostgreSQL superuser, every role's SCRAM verifier
(they are replicated to every server) and the ClientKey of every session opened **on it**. So it can act as any user
who signs in on it (it sees the password), run any SQL on itself and, through the sharding extension's node
connections, on the data routed to it, read what its own disks and memory hold, and try to guess passwords offline
from the verifiers. It cannot act as a user who never signed in on it, it receives no value from which another
user's ClientKey or any password-equivalent can be derived (forward goes to the leader, gather carries an
assertion), and it cannot make the leader or another member accept an identity it cannot prove. What a compromised
**leader** can do: everything (it holds the CA key, every verifier, the system database, and receives every
proof); that is inherent to a design in which the leader runs the cluster operations and checks the proofs.

## Cluster-wide reads (gather)

`listLogs`, `listAlerts` and `queryMetrics` answer for the whole cluster from any server. The server that
receives the request authenticates the caller and checks the role as for any request, then sends every other
server of the cluster the same query with `POST /internal/v1/gather`, in parallel, each call with its own
deadline (setting `gather-timeout`, default 3 s). The body is the one of `forward` with one more member,
`ordinal` (the ordinal of the server that is asked, used for the ids of its alerts); `operationId` is one of
`listLogs`, `listAlerts`, `queryMetrics` and `acknowledgeAlert`, `query` the caller's query string.

The answering server runs the operation through the same pipeline as a public request, with the identity the
leader's assertion vouches for (see "Gather: the leader's assertion"): **the role is derived again from the answering server's own catalog** (the check of
CP-07), so the caller needs the required cluster role on every server that answers a part, and a server that no
longer accepts the role (it was dropped or disabled there) answers `refused`. It answers its own part only, in a
form the merging server can order without ambiguity: log entries with their rank among the entries of the same
second, alerts with cluster-wide ids, metric series as the per-server resampled points; at most one more entry
than the page needs, at most 16 MiB in all.

The receiving server merges what came back with its own part. What a server answers is not trusted: entries are
about that server only (its id replaces whatever the answer says), text is cut and cleaned of control characters
(`peerclient.CleanText`), an alert id must carry the ordinal of the answering server, series must have exactly the
points that were asked for. A server that did not answer within its deadline, could not be reached, refused, or
answered something invalid is named in the response (`partial: true`, `missingServers[]` with `reason` `timeout`,
`unreachable`, `refused` or `invalidAnswer`); the others still answer. The cursors are keyset cursors over one
total order (logs: time, server id, rank; alerts: time raised, id), so a page boundary is the same whichever
servers answered; a cursor of a previous revision is refused with 400.

An alert's id is `ordinal << 32 | local id`: the ordinal is the number the leader gave the server when it joined
(`kingres_cp.server.ordinal`, sent to every server in the peer directory, `peers.json`). The id is unique in the
cluster, below 2^53 (what a browser holds in a JSON number), and tells the receiving server which server holds
the alert, so `acknowledgeAlert` goes straight to it (it audits the acknowledgement, once).

## Certificate renewal

Every server renews its own certificate (the server certificate and the client certificate are one certificate)
before it expires: when less than a configurable part of its lifetime is left (`certificate-renew-fraction`,
default a third) its renewal job (`internal/membership/certjob.go`; looks every `certificate-check-interval`,
retries after `certificate-retry-interval` with a doubling pause) sends `POST /internal/v1/pki/renew` to the
manager leader, which holds the CA key. The body is `{"csr": "<PEM request>"}`; the request must be made from
the key the server was admitted with and name only that server (the common name of the caller's certificate): a
server renews itself and nobody else. The answer is the new certificate, the CA certificate and the current
revocation list. An administrator can renew a server at once (`renewServerCertificates`): the leader asks the
server for a request (`GET /pki/csr`), signs it and sends the certificate with `POST /pki/install`.

- A leader that does not hold the CA key answers `503` with the code `ca_unavailable`; the job counts it as a
  failure. After three failures in a row the job raises the alert `certificateRenewalFailed` on its own server and
  audits the failure (`certificateRenewalFailed`, once per streak, and its end).
- A revoked server is refused by the transport (`certificate_refused`) before the call is read; if the record says
  `revoked` the leader answers `409 certificate_revoked`.
- The old certificate stays valid until it expires (it carries the same key); `revokeServerCertificates` revokes
  every certificate that was issued to the server and has not expired.
- Installing the certificate rewrites `server.crt` and reloads the instance (PostgreSQL re-reads `ssl_cert_file`,
  `ssl_ca_file` and `ssl_crl_file` on reload); the internal API listener, the connections of the sharding
  extension (`kingres_shard.node_conninfo` names the files) and the connections of kingresd read the files at every
  handshake. Nothing is restarted and open connections continue. The server then closes its idle connections to the
  other servers.

## Statement timeout of exec

The statement of `POST /internal/v1/exec` runs under `statement_timeout` of 15 minutes, set by the receiving server
on its own connection; the request context ends when the leader disconnects, but that does not stop a statement on
every path.

## High availability, part 1

### Heartbeats

`POST /internal/v1/heartbeat` (any server of the cluster, policy `AnyPeer`). Body
`{"intervalMillis": 1000, "uptimeSeconds": 12}` (both are durations; no time of day is ever sent). The receiver notes
the arrival on its own monotonic clock as "heard from the caller" (the caller is the server named by its certificate;
a server it does not expect is ignored) and answers `{"serverId": "<receiver>", "uptimeSeconds": 40}`. The sender
takes a matching `serverId` as proof that the receiver is alive. Each server sends one to every other server of its
peer directory every `heartbeat-interval` and skips a server whose previous call has not ended. A call has a timeout of
twice the interval (2 s at least, half the failure timeout at most). A call from a blocked peer is dropped by the
fault hook when it is on (tests only). Errors: `version_mismatch`, `certificate_refused`, `bad_request`.

### Leases

Authorization: both calls are `AnyPeer` (a server with a valid certificate); `POST /lease/grant` also needs the caller
to be a server of this server's peer directory (`403 not_member` otherwise). The holder is **the server named by the
caller's certificate**, never a field of the body.

`POST /lease/grant`: the caller asks for the lease of a shard group.

```
{"group": 1, "durationMs": 10000, "dryRun": false}
-> 200 {"granted": true, "holder": "10.0.0.12"}
-> 200 {"granted": false, "holder": "10.0.0.11", "waitMs": 8200}
```

`durationMs` is the validity the caller wants from the start of its renewal round (1 ms to one minute; `400
bad_request` otherwise). The grantor answers `granted: true` when it holds no lease for the group, when the caller is the
holder, or when the holder's lease expired more than the margin ago. Otherwise it answers `granted: false` with the
current holder and `waitMs`, the time until it would grant to another holder (a duration; no time of day travels).
A grant that changes the holder is on disk (`<data-dir>/lease/grants.json`) before it is answered; if it cannot be
written the answer is `503 unavailable` and nothing was granted. `dryRun: true` answers what would happen and changes
nothing (the tests use it to see the earliest moment a new holder could be granted; part 2 uses it to wait for the old
lease). The call is refused while the server is not clustered (`409`/`not_available` through the call table).

`GET /lease/state`: this server's knowledge of the leases.

```
{"server": "10.0.0.11",
 "grants":  [{"group": 2, "holder": "10.0.0.12", "remainingMs": 7300}],
 "leases":  [{"group": 1, "holder": "10.0.0.11", "state": "held", "remainingMillis": 3900, "enforced": true}],
 "durationMs": 10000, "marginMs": 3000}
```

`grants` are the leases this server granted (remaining time, margin not included); `leases` merges the leases this server
holds or lost (`state` `held`, `lost`) with the ones it granted to others (`granted`). `enforced` tells whether losing
the lease stops the instance. `state` `none` is a group whose lease this server has not held yet in this run, for example
while its primary instance waits to be started until the lease is held (the wait marker, README "Decisions (leases)" 7):
nothing was lost, so no `leaseLost` event or alert exists for it.

`durationMs` and `marginMs` are the lease duration and the margin of the answering server (added with the failover groundwork):
the safety argument needs them equal on every server, so a failover compares them first and refuses when two servers differ.

**Hand-over and release (added with the failover groundwork).** `POST /lease/grant` also takes

```
{"group": 1, "durationMs": 10000, "transferTo": "10.0.0.12"}   -> 200 {"granted": true, "holder": "10.0.0.12"}
{"group": 1, "durationMs": 10000, "release": true}              -> 200 {"granted": true}
```

`transferTo` is executed only when the caller (named by its certificate) is the holder of record at this grantor, even when its
lease has not run out: the holder becomes the named server (which must be in the peer directory, `400 bad_request` otherwise) for a fresh
duration from the receipt, the change is on disk before the answer, and there is no instant at which the group has no holder, so the
old holder cannot be granted it again. From any other caller it answers `granted: false` with the holder and `waitMs`. `release` deletes
the grant of the caller when it is the holder (a group with no grant answers `granted: true`); it is for a holder that has confirmed that
no primary runs under the lease and that its fence marker is on disk. Neither lets anybody but the holder move a lease: the argument of
"Why this is safe" in the README holds unchanged. The caller of `transferTo` is responsible for not acting under the lease any more.

Fault hook (tests only, `fault-dir`): a call from a server listed in `blockInbound` is dropped without an answer after
its certificate was verified, and a call to a server listed in `blockOutbound` fails as unreachable, before the network
is used. Nothing of it exists unless `fault-dir` is set.

All five calls are made by the manager leader (policy `LeaderOnly`, also to itself, where the call is answered in

### The fencing epoch of task steps

A step of a task run that calls another server sends the header `X-Kingres-Fence: <task id>:<epoch>` (the lease epoch
of the run, `task.Env.Fence()`). A server that receives it on a call of a leader-only policy (`LeaderOnly`,
`LeaderOrJoining` from a known leader) keeps the highest epoch seen per task, in memory and in
`<data-dir>/fence.json`, and answers a lower epoch with `409 fenced` before it does anything; an equal or higher epoch
is accepted and recorded. A malformed header is `400 bad_request`. The header is ignored on calls of other policies
and from callers that are not the leader, and a call without it is never fenced.

An unknown leader is asked for again (three times, 200 ms apart) before a leader-only call is refused with
`not_leader`; a joining server is not asked.

### The calls of the failover task (increment 3)

Types: `internal/failover/types.go`, handlers in `cmd/kingresd/failover.go` and `internal/standby/failover.go`. Every one is `LeaderOnly`; the
leader calls its own handler directly for itself. Each carries `expectedTerm`, the catalog term the run read when it started, and the callee refuses
it with `409 stale_term` when its own catalog has a newer one (somebody promoted meanwhile). The calls are **not** versioned: the internal API
version stays "1". A server of an older version answers `404 not_found` to a call it does not know, which a step reads as "older version" (and
refuses the failover with `version_mismatch` at the request), never as `no_instance`, which is a real answer ("this server runs no instance of the group").

| Call | Does |
|---|---|
| `POST /failover/lease` `{group, role: fence|holder|release, transferTo, expectedTerm}` | `fence`, `holder`: adopt the lease of the group (renewed like a holder's) and answer `{held, rounds, waitMs, refusedBy}` from the last round; with `transferTo`: hand the lease to that server (`{transferred}`); `release`: stop renewing it. |
| `POST /failover/demote` `{group, mode: immediate, expectedTerm, transferTo}` | on the old primary's server: relinquish the lease (marker), stop the instance with an immediate shutdown, confirm it does not run, only then hand the lease to `transferTo`; `{stopped, transferred}`. `409 not_primary` when the server runs no primary of the group. | With `mode: "fast"` (the switchover) the call stops the instance with a fast shutdown (never immediate), reads `pg_controldata` and answers `{stopped, clusterState, checkpoint, released}`; the lease is released at the grantors (free at once) only when the state is `shut down`. It is idempotent: a stopped instance is read again, which is how the proof is made a second time.
| `POST /failover/promote` `{group, standbyId, instanceId, expectedTerm, reapplyList}` | on the standby's server: empty `synchronous_standby_names` and reload, write the role file (primary, origin copy), check that the server holds the group lease as the last thing before `pg_promote(true, 60)`, then `Attach` the lease to the instance (watchdog); `{status: promoted|already, timeline, lsn}`. `409 lease_not_held`, `409 not_standby`, `409 stale_term`; `503 unavailable` when `pg_promote` did not finish (repeat). |
| `POST /failover/prepared` `{group, database}` | on the promoted instance's server: `kingres.recover_prepared_transactions()` on the instance that is the group's primary, READ COMMITTED (the extension asks for it on the promoted node and on the map group primary). `409 not_primary`; `503 unavailable` (repeat). Repeating it is harmless. |
| `POST /failover/quiesce` `{group}` (leader) | the planned switchover, S2: this server stops the writes of the primary of the group. - `quiesce`, `mark` and `verify` need the fence header of a task run (`400 bad_request` without it, as `demote` and `promote`); `unquiesce` and `resume` do not

- `POST /failover/map/start`: a call that came from a member is always handled as manual (the candidate monitor starts an automatic bootstrap on its own

### The ledger keys (ledger phase 7, step 4)

Types: `internal/ledgersign/agent.go`. The three calls are `LeaderOnly` and carry the fence of the task run like every leader-only call. The leader
calls them from the steps of `ledger.key.create`, `ledger.key.rotate`, `ledger.key.distribute`, `ledger.key.retire` and `ledger.key.revoke` and from the job
`ledger.key.sync`. A server that is not a holder never has a key file: the leader sends one to the servers that run an instance of shard group 0 (the candidates
of the manager leader) and takes it away from a server that stops running one and from every server when the key is retired or revoked. The body of an install
holds the seed in clear when the leader's key files are plain: it crosses only the mutually authenticated listener and is never logged (the internal API logs
no body), and neither the callee nor the leader puts the file in an error, a task detail or an audit entry. A call made inside a task step is repeated by the peer client
after a failure of the connection that left the effect unknown (the rule of every step); an install is a no-op when the key is already there, and a remove when it is not, so
the repeat and the step that runs again are safe.

### The ledger read and publication calls (ledger phase 7, steps 5 and 6)

Types: `internal/ledgerround/wire.go`; the callee is `ledgerround.Reader` (`ledger/read`) and `ledgerround.Files` (`ledger/publication/get`). `ledger/read` is `LeaderOnly`: the collector of the manager leader reads each shard group from the server that runs its primary, once per round (`head`, or `digest` when a digest is asked for), then the blocks it needs (`entries`, at most 10 000; the first one is the last published block, so that its hash is compared with what was published). A call about a group names the group, because a server can run the primary of more than one group after a failover; the callee refuses with `409 not_primary` when it does not run it, and the leader counts the group as unread in that round (its aggregate members are `stale`, the digest is incomplete and names the group). The call takes no SQL text, the database name is checked as an identifier, and the answer holds block headers (87 bytes each), the head, and the digest the extension made, never a row. A read of a group that this server runs stays in the process. `ledger/publication/get` is `ToLeader`: a server whose publication listener got a request asks the leader for the file and keeps the immutable ones (tiles, bundles, events) in a bounded cache; a file that is not there is `404 not_found`, which the listener answers as a 404. Both calls are reads, except `digest`, which records a digest in the database it reads (as `ledger_generate_digest` does); a repeat after a lost answer only records another one.

### A server that waits for its lease

A server whose instance is held back until its group lease is won (the fence marker `<data-dir>/lease/fenced.<group>` or the wait marker `<data-dir>/lease/waitlease.<group>` of the group of the instance exists (a marker without the suffix, left by an earlier version, holds for every group until the first lease round renames it), or its instance is not running) cannot read the catalog and knows no leader. Every call that needs the leader (`LeaderOnly`, `LeaderOrJoining`, `ToLeader`) is then answered `503` with the code `service_unavailable` and `Retry-After: 2`, never `403 not_leader` (which means "the caller is not the leader"). The caller treats it as transient: a task step retries with a pause growing from 1 s to 8 s for up to 5 minutes and then fails naming the server; other callers get the 503. The REST sign-in on that server answers `503 service_unavailable` with `Retry-After: 5` in the same window.

## Configuration

Phase 13 (contract 0.8.0, design `config-phase13.md`). The leader asks every server for its state, then for the apply of a
revision; the server never takes a path, a program name or SQL text from the request: the values are rendered into a file
by `instance.RenderConfig` (checked name, quoted value), the database values are built by PostgreSQL's `format()`. The
calls refuse managed and refused parameters again on the server. The clock probe is an exchange of one request: the asker
reads its wall and monotonic clocks before and after, the answer carries the other server's wall clock.

## Errors

JSON `{"error": "<code>", "message": "..."}`. Codes: `no_certificate`,
`certificate_refused` (401), `version_mismatch` (409), `not_leader` (403),
`not_found` (404), `identity_unproven` (401: the proof of a forwarded or gather-authorize request, or the assertion of a gather request, is missing or wrong), `not_member` (403: the caller holds a certificate but is not a member of the cluster), `forbidden` (403: a task call about an instance that is not the caller's), `bad_request` (400), `statement_failed` (422), `ca_unavailable` (503: the leader does not hold
the CA key), `certificate_revoked` (409), `fenced` (409: the task run that made the call was superseded by a newer one), `failed` (500).

### Repeating a call (review ST-03)

A client that did not get an answer repeats a call that a task step made (the connection broke under it) at most three times with the same
fence token; a client time limit that ended after the connection was made is not repeated. What the second execution of each call does:

| Call | Second execution |
|---|---|
| `POST /instance/create` | no-op when the instance exists (it trusts, starts, waits) |
| `POST /instance/start`, `/stop` | no-op (under the lifecycle lock; the wait for the lock ends with the caller's context) |
| `POST /instance/remove`, `/node/finish`, `/node/reset` | no-op, or answered as done / certificate refused |
| `POST /instance/trust`, `/pki/install`, `/peers`, `/config/apply`, `/standby/plan`, `/globals/apply` | rewrite the same files or rows and reload |
| `POST /apply` | `database.create` checks that the database exists; the other kinds were not all read |
| `POST /standby/create`, `/remove` | no-op (they check what exists), serialized by the agent |
| `POST /standby/rebuild` | **no-op for a standby that is of the generation asked for** (changed in this step); the rebuild of an old primary resumes where its mark says it stopped: a rewind that was interrupted is repaired by a base backup, one that finished is not done again |
| `POST /config/restart` | **no-op with `ifPending` when nothing waits for a restart** (changed in this step; a call without it restarts) |
| `POST /failover/freeze`, `/unfreeze`, `/standbys-gone` | set the same state in memory |
| `POST /failover/lease` | adopt again (no-op), a transfer from a server that is no longer the holder is refused (`transferred: false`; the step then reads `/failover/state`), `release` of an adoption that is gone is a no-op |
| `POST /failover/demote` | no-op for a stopped instance (the marker exists, the stop is confirmed, the transfer is refused from a non-holder); `409 not_primary` once the instance is not the primary of the group |
| `POST /failover/promote` | `already` for an instance that is out of recovery (it re-applies the empty list and attaches the lease); a promotion that did not finish is asked again |
| `POST /standby/repoint` | no-op when `primary_conninfo` and the slot are the ones asked for; only waits for the walreceiver |
| `POST /lease/grant` | a renewal; `transferTo` by the caller that is no longer the holder is refused (`granted: false`); `release` of a free group answers `granted: true` |
| `POST /task/record`, `/settle`, `/reserve`, `/leave-cluster`, `/leave-status`, `/add-server`, `/forward`, `/pki/renew`, `/exec`, `/heartbeat` | made by servers outside a step, or repeated by design; not repeated by the client |
| `GET` calls | reads |

The failover steps (increment 3) are no-ops on a second execution in the same way: each checks what exists before it acts (the pinned standby in
`failover_group`, the state of the callee from `GET /failover/state`, the catalog from `kingres.node`), and a client time-out is read as "the call did not
finish": the step asks the callee what it did and then decides, it does not repeat blindly.
