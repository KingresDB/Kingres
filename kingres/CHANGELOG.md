# Changelog

All notable changes of KingresDB are listed here, by release. A release is made for PostgreSQL 18 and PostgreSQL 19 at the same time from one source, and has one version (`kingres_version` in the top-level `meson.build`); see [docs/dev/releases.md](docs/dev/releases.md). The dated, detailed record of the work is [docs/worklog.md](docs/worklog.md), and the independent reviews are in [docs/reviews/](docs/reviews/).

The release script ([packaging/release/release.sh](packaging/release/release.sh)) takes the notes of a release from the section of this file whose heading is `## [<version>]`, and refuses while that section has a `### Pending` part. The section of the first release is written from the integration branch of the first release on 2026-11-24 (everything planned for the first release except the version bump and the tag); its Pending part lists what is still open and is removed, with the items it lists done or moved out, at the real release.

## [Unreleased]

Nothing yet. The changes planned for the first release are in the section below.

## [0.1.0] - not released

The first release. KingresDB is a thin fork of PostgreSQL 18.7 and PostgreSQL 19.0 with sharding, a tamper-evident ledger, a control plane and a web console, and extensions for analytics. The REST contract is 0.33.0.

### Added

- **Bases.** PostgreSQL 18.7 (`kingres-18`, upstream tag `REL_18_7`) and PostgreSQL 19.0 (`kingres-19`, upstream tag `REL_19_0`).
- **Fork and packaging.** A thin fork with a small register of core patches ([docs/dev/core-patches.md](docs/dev/core-patches.md)); one source of every extension for PostgreSQL 18 and 19 ([ADR 0023](docs/adr/0023-one-extension-source-for-several-majors.md)); KingresDB code under the AGPL-3.0-only, PostgreSQL code keeps its licence ([ADR 0024](docs/adr/0024-agpl-for-kingresdb-code.md)). A reproducible release build, a Debian package per major (`kingres_<version>+pg18-<revision>_amd64.deb`, `+pg19`), a container image per major (`kingres:<version>-pg18`, `-pg19`), a three-node development cluster in Docker Compose ([kingres/packaging](packaging/README.md)), and a release script with its test.
- **Security hardening of the extensions.** `kingres_shard`, `kingres_ledger` and `kingres_columnar` do not trust a schema that lets another role create objects, an extension catalog that is not the installed extension's own, or a registry that cannot be trusted (the ledger refuses `UPDATE`, `DELETE` and `TRUNCATE` of a table that looks like a ledger table while it cannot be); the check of the schema runs in every install and upgrade script; the search path of the privileged SQL of `kingres_shard` is fixed; what the extension moves into the schema `kingres` belongs to the bootstrap superuser. `kingresd` raises the alert `extensionSchemaUntrusted` (contract 0.24.0) and reads nothing in a schema that it does not trust; copying extensions to an added server checks the package, the schema owner and the leader's version. An owner difference of an extension schema on an added server skips that extension and raises the alert `extensionSkipped` (contract 0.30.0), one alert for each skipped extension (subject `server:<id>|database:<name>|extension:<name>`), which clears when a later apply of the extension on that server succeeds or the database is dropped; the schemas `kingres` and `kingres_*` are refused to other extensions.
- **Sharding** (`kingres_shard` 0.9). Tables split into hash buckets over several servers; writes and reads on any server; two-phase commit with recovery; reference tables; distributed DDL; bucket moves with logical replication; standbys, `promote_node`, prepared transactions across a failover, distributed deadlock detection and coordinated restore points.
  - Pushdown (phase 2b): closed queries, partial aggregation, sorted streams with limit and joins of colocated tables run in the shard groups, and a row router for multi-row `INSERT`, `INSERT ... SELECT` and `COPY FROM`; the complete scan stays as the fallback for every query ([ADR 0022](docs/adr/0022-the-complete-scan-stays.md)).
  - Table lifecycle (phase 9): distribute a table that already holds rows, in blocking and online form; turn a table back into an ordinary table; change the distribution column, the bucket count or the colocation group; distribute user-partitioned tables; carry dependent views and storage parameters.
  - Elasticity (phase 10, 0.8): splitting a bucket, weights per server, plans by disk size. The locks of a split are bounded and never left behind, and the recovery worker no longer undoes a split between its record and its live mark.
  - Bucket moves (`kingres_shard` 0.9): the session that runs a move holds a lock of (colocation group, bucket) from before the record of the move is written until it holds the live mark, so the recovery worker can no longer undo a move under its session however long the session stalls; the waits are bounded and one handler lets go of both locks (fault points `move_after_begin`, `move_after_mark`). An old copy (or old partition of a split) that objects of its owner depend on (a view, a materialized view, a foreign key, a function on its row type) is left in place, never dropped with `CASCADE`: the record of the move or split says what depends on it, `check_cluster()` reports `orphan_blocked`, and the next cleanup pass after the owner dropped them finishes the move (before, the cleanup failed silently at every pass).
  - Distributed schemas (phase 11, 0.8 and 0.9): a schema placed and moved as a unit, schemas in the rebalance plan and the drain, and the schema checks of `check_cluster`.
  - Analytics (phase 12, 0.9): repartitioned joins on columns other than the distribution column, `MERGE` on distributed tables, columnar tables that can be distributed and moved (blocking variants), approximate `count(DISTINCT)` through `kingres_sketch`, and the explicit refusal of ledger tables by `create_distributed_table` and `create_reference_table` (SQLSTATE `KS016`).
  - Own SQLSTATEs `KS017` to `KS022` for the refusals that the control plane tells apart (no receiving shard group, unreadable bucket sizes, a busy bucket, a pinned schema, a failed verification, a call on a node that is not the map group primary, which was `KS010`); a split of a table without a primary key is refused with `0A000` instead of `55000`; `kingresd` matches the code, not the wording (README of `kingres_shard`, "SQLSTATEs of the answers").
- **Control plane** (`kingresd`, REST contract 0.33.0). Cluster creation and joining, servers, roles and grants, network access, databases, tasks, alerts, logs and metrics; the manager leader on the primary of the map group, the cluster state in a system database, certificates with renewal and revocation.
  - Rebalance as a task with stop, resume and reports; strategies by bucket count or disk size, a threshold, weights, several moves at a time, an automatic mode (off by default), draining a server, splitting a bucket (phase 10). A drain hands the map group over by a planned switchover (step 4, contract 0.27.0), and a rebalance is held back, or refused with `group_degraded` unless `force` is sent, while a standby lags by more than `maxStandbyLagBytes`.
  - Time partitioning of distributed tables (phase 12, contract 0.25.0, `kingres_timepart` 0.3): policies, plans and runs on a user-partitioned distributed table; partitions created ahead on every server that holds a bucket, old leaves converted to columnar storage, expired partitions dropped or detached.
  - `pg_stat_statements` is preloaded by every instance and created in every database that `kingresd` makes (`kingresd` does not install it in databases that already exist); `plpgsql` is installed in every such database. Its settings can be set from the Configuration page.
  - Distributed schemas: distribute, move and make local as tasks, and the sharding mode of a database (phase 11). A rebalance and a drain plan and move distributed schemas as items of the plan (contract 0.31.0): `kind` and `schemaName` in the plan, the progress and the report; a schema that cannot move (pinned by a ledger table, or a table without a key) refuses the drain before a task exists.
  - Failover inside `kingresd` fenced by leases: manual failover, failover of the map group, automatic failover with a counter, planned switchover of an ordinary group and of the map group, restore of preferred primaries, and the call that gives up a stuck map group bootstrap (phase 5, rounds 1 and 2).
  - Hard failover of the map group while its server is alive (contract 0.28.0): the leader judges the loss, fences its own primary of the map group and hands the lease to a standby's server; `abandonMapGroupBootstrap` takes `lostServerId` to declare a lost candidate (with one standby of the map group a dead candidate leaves every REST call answering 503). A switchover ends when the held-back old server forgot the leader: state, unquiesce and unfreeze are accepted from the leader named by a majority of ready members.
  - Local recovery of a map group that is held back for good (contract 0.34.0, audit action `releaseMapGroupHold`): `kingresd -release-map-hold -lost <serverId> -accept-data-loss`, run on the server of the old leader with `kingresd` stopped, ends the hold when the candidate died and the cluster has only one standby of the map group, so that REST answers 503 everywhere; it refuses without both words, for the local server, while the data directory is in use (a lock of the data directory, taken by every `kingresd`), for another server than the one the hold was made for, and while a bootstrap is in progress; it is audited and logged. The declaration `lostServerId` of the abandon call carries the proof of the operator's session and goes only to the server whose primary of the map group is held back; that server checks it against the keys of the administrators that it cached on disk while its system database ran (it can read no verifier while it is held back), so one member's certificate is not enough to forge it; the lost server must be seen dead (not suspect or unknown) before and right before the release, is asked as well, and a declaration that releases nothing is an error. The command is repeatable after a crash, takes no directory it did not find, and a failed stop of a promoted instance is repeated. A promoted instance whose adopted lease was lost before it was attached is stopped by the lease code, and a server that runs the lease protocol does not start without the program `kingres-watchdog` (setting `allow-no-watchdog` for tests and development).
  - Review of phase 5 (high availability, contract 0.33.0): a group lease is enforced only once a standby that a failover may use is ready (the leader makes a record ready only after the primary's server took the list with the entry ready), so a primary is no longer fenced while its first standby is being copied; the lease rounds of the groups of one server run side by side and the topology is read outside them; the wait for the fence lease ends for a lease call that keeps failing (a failover pauses, a switchover rolls back with `lease_unavailable`) and renews the freeze; the freeze call needs the fence header of a task run; the declaration `lostServerId` reaches the old leader with the proof of the operator's session, checked against cached administrator keys because that server is held back; a hard failover of the live map group that accepts a loss of data needs `kingres_admin`; fences and leader questions run side by side, and a transfer of a lease writes its marker first.
  - Second review of phase 5 (no contract change): the lease check loop no longer waits for the slowest fence, and a group is never fenced twice at once; a standby that becomes ready cannot be taken back to not ready by a list built at the same moment, and the final list after it must reach the primary's server; a lease round takes its place (first come first served) before its group lock and reads the topology only then, so releasing a group does not wait behind other groups' rounds; a failed renewal of the freeze no longer ends a graceful switchover without rollback; the wait for the lease counts only continuous errors; a failover that pauses in that wait releases its fence adoption; a restart after a crash in the middle of a lease transfer that never reached this server's grantor renews the group again.
  - Escrow of the key of the certificate authority (contract 0.26.0, `getCaEscrow`, `setCaEscrow`, `rotateCaEscrow`; off until switched on; the Certificate authority tab of the Security page shows and changes it): a new manager leader opens its own sealed copy and goes on issuing, renewing and revoking certificates.
  - Export and import of a whole database are in the entries below (phases 14b and 14c).
  - Table lifecycle tasks (phase 9, increment 9.6).
  - Distribute with related tables and the operation indicator of a table (phase 9, contract 0.32.0). `listRelatedTables` gives the plan: the ordinary tables that foreign keys link to a table (the whole closure, not through a table that is already distributed), the column each would get, the keys, and what would stop it. `distributeTable` takes `relatedTables` and distributes them together with the table in one task, colocated with it: the keys between the tables are taken out, each table is distributed in a step of its own (a run that is repeated skips the tables that are done), and the keys are added back `NOT VALID` and validated; a failure puts the keys back where it can and names the ones it could not. Only the blocking copy is used. `Table.operation` in `listTables` and `getTable` says which long operation runs on a table (from the tasks, with the related tables of a distribute, and from the extension's own records, also those started from SQL). The console lists the related tables in the Distribute dialog, shows the operation as a badge on the row and a line on the table page, and turns the conflicting buttons off. Design: [docs/design/shard-phase9.md](docs/design/shard-phase9.md).
  - Analytics (phase 12, contract 0.18.0): approximate aggregates per database, conversion of a table or partition between row and columnar storage with a preview, time-partitioning policies with a plan, runs and a scheduler, and the preload of `kingres_columnar`. Conversion and policies are open for tables of superusers unless the cluster setting `analytics.allowNonSuperuserOwners` is on.
  - Configuration of PostgreSQL parameters and time from the console, with preview warnings (phase 13).
  - Export and import of a table as CSV (phase 14a, contract 0.19.0): resumable uploads and downloads of sealed staged files, all-or-nothing import with a commit marker, off until the cluster setting `dataTransfer.enabled` is on. The search path of the service connections is fixed, and the marker tables have row security and a checked tag.
- **Database export and archive validation** (phase 14b, REST contract revision 0.29.0). `exportDatabase` writes one zip archive of a database (the structure from `pg_dump` of the same build, taken by the service role and normalised; a catalog document for the distribution, the access methods, the ledger and time-partition policies and the sequences; one CSV entry per table; a manifest with SHA-256 sums) and `validateDatabaseArchive` checks an uploaded archive without touching any database. The console has the dialogs and the report page. The archive can be checked, loaded by hand, or imported (below). Design: [docs/design/data-export-import.md](docs/design/data-export-import.md).
- **Database import** (phase 14c, REST contract revision 0.30.0). `importDatabase` creates a new database from an archive made by `exportDatabase`. The archive is read again from its bytes and every statement is classified before anything is made; the structure is loaded as the importing role into a private database that only the service role can reach during its own steps, every table the role made is locked and checked before the service role acts on it, the distribution, ledger (a new chain, verified) and time-partition policies (switched off) are set again, and the database gets its final name only at the end. A failed import removes the private database. A role that is dangerous, or that has a login member that can act as it, is refused; the free space of every server is checked against the expanded archive; the ledger starts a new chain ([ADR 0028](docs/adr/0028-ledger-tables-are-carried-as-data-and-restart-their-chain.md)); time-partition policies come back switched off. The guide: [section 13 of the operator guide](docs/guide/operator-guide.md#13-export-and-import-of-a-database). The console has the dialog and the report page. Design: [docs/design/data-export-import.md](docs/design/data-export-import.md).
- **Console.** A Vue 3 web console on every node: dashboard, servers, shards, rebalance, replication and failover, databases, tables (the table page with the lifecycle dialogs of increment 9.7), security, configuration, settings, ledger, workbench, alerts, tasks, logs and this server. The analytics console (approximate aggregates, the Storage column, partitions, policies and their runs, the plan summary in the workbench) and the transfers panel with the export and import dialogs. The Certificate authority part of Security shows and changes the escrow of the CA key (contract 0.26.0); the Extensions tab of Configuration says whether `kingres_columnar` and `pg_stat_statements` are preloaded on every server; the failover dialog of the map group can declare the candidate server lost (`lostServerId`, contract 0.28.0).
- **Ledger** (`kingres_ledger` 0.3). Append-only and updatable ledger tables with blocks, digests, inclusion proofs and verification; client signatures with a signature policy per table; a write guard; signing keys, a transparency log per chain and an aggregate log per database published on a listener of its own; anchoring to a WORM object store, an RFC 3161 authority and OpenTimestamps; bundles and the audit of the publication; the acknowledgement of a diverged chain; the acceptance of a restored system database as a signed event ([ADR 0025](docs/adr/0025-restore-of-the-system-database-is-accepted-by-an-operator.md)); a rotation generation of the credentials of anchor targets.
- **Verifier** (`kingres-verify`). A standalone, standard-library Go command that checks digests, proofs, signed checkpoints, tile logs, consistency proofs, aggregates, bundles, client signatures and anchors without trusting the database; a reproducible build and a release script that produces signed checksums.
- **Analytics extensions.** `kingres_sketch` 1.0 (distinct count, top-n and percentiles, with partial aggregation that the shard groups compute); `kingres_columnar` 0.2 (an append-only columnar table access method with B-tree indexes, parallel scan, logical decoding of inserts and reuse of free space); `kingres_timepart` 0.3 (time partitions created ahead and dropped by policy, conversion of old partitions to columnar storage and back, and policies on user-partitioned distributed tables).
- **Documentation.** A user guide ([docs/guide](docs/guide/README.md)): quickstart, installation, operator guide, upgrade and limitations.

### Pending (open items; this part is removed at the real release, with each item done or moved out)

- **Done, moved into the sections above (kept here as a record until the release removes this part):**
  - Phase 5, hard failover of a map group leader that is alive: done (contract 0.28.0, with `lostServerId`; five cluster tests on both majors). Escrow of the certificate authority key: done (contract 0.26.0, off until switched on).
  - Phase 10, drain step 4 (hand-over of the map group, contract 0.27.0) and the standby lag rule (`maxStandbyLagBytes`, evaluated at the start and inside a run, and for the automatic mode): done.
  - Phase 12, time partitioning of distributed tables: done (`kingres_timepart` 0.3, contract 0.25.0). The conversion of a whole distributed table by hand stays refused, as stated in the guide.
  - Phases 14b and 14c, export and import of a whole database: done (contract 0.29.0 and 0.30.0); they are now part of the first release.
  - Phase 11, schema items in the rebalance and the drain: done (contract 0.31.0). Phase 9, distribute with related tables and the operation indicator of a table: done (contract 0.32.0).
- **Phase 5, still open:** the hardening loops of the whole failover part: `run-failover-loops.ps1` ran one round of every group on both majors (28 of 28 on 19.0; 27 of 28 on 18.7, the failure, a timeout of `TestSwitchoverSurvivesACleanStopThatOutlastsTheLease`, has no found cause) and not the repeated runs that the design asks for; two reviews of the part were made, and what is still open is that the loops are not repeated. The positive cluster test of `lostServerId` with a second standby of the map group is not done (unit tests only). Added since: a planned switchover of the map group survives a clean stop that outlasts the task lease (the step lengthens the lease to about 105 s before the stop; a stop that outlasts even that rolls back as before). The cost is that, if the old leader ends during the stop, the new leader takes the task over up to about 105 s later. The restore of preferred primaries (`TestSwitchoverAndBack`) failed in 3 of 4 full runs of `^TestSwitchover` made after the start wait of the stop and in 2 of 4 later full runs of the same code (and in none of its runs alone) with `lease_held_elsewhere` and no server named. The cause found, and shown by unit tests, is that the wait for the lease asks for the adoption again every second and, for a group that the cached topology names to this server (the leader is the old primary of a restore), each ask wiped the rounds that the renewal pass had just run, so the lease never showed as held; an ask now wipes them only when the group was given up or is not named. That the change removes the failures of the cluster test is shown only by the full runs after it (the counts are in the log of the branch), not proven. The repeated clean stops (Verify, Promote) ask only for the proof and no longer release the lease. This item is not a reason to call the phase done.
- **Instance start (phase 5):** starting an instance whose postmaster is still shutting down now waits for the shutdown (up to the stop timeout) and then starts it, or reports an error; before, it reported success while the instance went down. This is what the rollback of a stop that outlasted its call needs.
- **Phase 7, step 24, dropped from the first release:** an external signer command, publication mirrors and the anchor probe from another server.
- **Phase 8, future roadmap, not part of the first release:** a global snapshot and a multi-node ledger.
- **Phase 14, open:** the free space of the data nodes is checked against the expanded archive of an import, but a leader that changes at every step of an import is not tested on a cluster, and a distributed-schema database is not covered by a round-trip test. The Extensions tab shows only whether each extension is preloaded; the install state of a database is not shown in the console because nothing reports it.
- **Release items, open:** a reserved WAL resource manager id for `kingres_columnar` (it still uses the experimental id 128, `RM_EXPERIMENTAL_ID` in `kingres_columnar.h`); the packages and images of the final contents run through the package tests on a machine with Docker (the shell tests of the package, the image and the compose cluster were changed for `pg_stat_statements` and not run); the tests of the C and SQL of the merged tree on both majors (`g2` was checked on Windows only for the Go code, the console and the contract); the final checks recorded for both majors on the release commits; the version bump and the tag.

### Known limitations

No global snapshot across shard groups (phase 8, a future roadmap item); no move of a cluster between PostgreSQL majors; no signed packages, no apt repository. The full list is in [docs/guide/limitations.md](docs/guide/limitations.md).
